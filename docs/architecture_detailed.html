docs-mcp 상세 아키텍처

API 명세(OpenAPI)와 팀 협업 문서(Drive/Notion)를 키워드+벡터 하이브리드 검색(RRF)으로 색인해, MCP 프로토콜로 호출 LLM에 근거 문서를 공급하는 검색 서버. 최종 자연어 답변은 서버가 만들지 않는다 — 서버는 후보 피더다.

1. 시스템 흐름

두 진입점(MCP 서버 · 배치 스케줄러)이 하나의 서비스 계층을 공유하고, 검색은 항상 키워드(FTS)와 벡터(HNSW) 신호를 RRF로 융합한다.

2. 컴포넌트 의존 구조

화살표는 데이터 흐름이 아니라 의존 방향이다 — A → B 는 "A가 B를 임포트·호출한다"는 뜻. 위에서 아래로만 흐르는 것이 규칙이고, 그 규칙에서 유일하게 면제된 지점은 아래 별도 인셋에 따로 뽑았다.

3. MCP 표면 — 16 tools + 1 resource

도구 함수는 얇다. 인자 검증 → 서비스 호출 → 페이로드 변환이 전부이고, 예외를 MCP 오류 응답 {error, code, message}로 바꾸는 일은 run_bundle_tool 하나가 전담해 16개 도구가 같은 실패 규약을 공유한다.

4. 검색 파이프라인

두 검색 표면 모두 RRF로 융합하지만 arm 구성이 다르다. 점수는 score(d) = Σ 1/(K + rank(d))이고 K = 60은 표준값으로 고정해 env로 노출하지 않는다 — 평가셋 없이 튜닝할 근거가 없기 때문이다.

표면arm 구성융합 키롤백 스위치
search_endpoints 2-arm — keyword(to_tsquery + ts_rank) · vector(코사인 · HNSW) ref_id rrf(기본) / fallback
search_documents 3-arm — title(제목·URL 토큰 매칭) · keyword · vector Document.id indexed(기본) / fetch
MECHANISM

스케일이 다르면 더하지 않는다

ts_rank와 코사인 유사도는 단위가 달라 가중합할 근거가 없다. 그래서 점수 대신 각 arm 안에서의 등수만 쓴다. 동점은 키 오름차순으로 깨 결정적 결과를 보장한다 — 골든 회귀 테스트의 전제다.

MECHANISM

미색인 문서도 죽지 않는다

title arm의 키를 deterministic_document_id()로 순수 계산해, 본문이 아직 색인되지 않은 문서(document_meta.document_id가 NULL)도 keyword/vector arm과 같은 키 공간에서 만난다. 별도 폴백 분기 없이 제목 신호만으로 결과에 남는다.

MECHANISM

의미 검색이 불가능하면 끈다

임베딩 백엔드가 해시 폴백이면 벡터 arm에 의미 유사도가 없다. 이때는 무거운 모델을 로드해 판별하지 않고 설정값만으로 vector arm을 비활성화한다.

5. 검색 품질 측정

이 프로젝트에서 가장 값이 나간 작업은 튜닝이 아니라 자기 수치를 반증한 것이다. 초기 지표는 20개 엔드포인트짜리 합성 하네스에서 나온 값이었고, 실제 규모의 코퍼스를 프리즈해 다시 재면 절반 이하로 떨어졌다.

측정 조건코퍼스Recall@1Recall@3Recall@10MRR
합성 하네스 (초기) 엔드포인트 20개 68% 88% 95% 0.788
실 코퍼스 (현행) Stripe 589 + GitHub 1,220 15% 25% 50% 0.248

현행 값은 질의 변형 라우팅을 포함한 rrf 전략 기준이고, 질의 수는 n = 20이라 표준오차가 ±11%p대다 — 소수점을 다툴 수치가 아니라 어느 축이 무너지는지를 읽는 용도다. 코퍼스는 핀 SHA로 고정해 저장소에 프리즈했고, 재현 커맨드 한 줄로 다시 돌릴 수 있다.

FINDING

합성 벤치는 포화됐던 것

엔드포인트가 20개뿐이면 어떤 검색기도 상위권을 채운다. 589~1,220개로 늘리자 변별력이 처음으로 드러났고, 초기 88/95%는 성능이 아니라 벤치의 한계였음이 확인됐다.

FINDING

무너지는 축 1 — 교차언어

한글 질의로 영문 문서를 찾는 축(C2)이 사실상 0에 가깝다. 코퍼스가 커지며 타 언어권 decoy가 늘어난 영향으로, multilingual 임베딩 모델의 한계가 그대로 노출된다.

FINDING

무너지는 축 2 — 512토큰 상한

파라미터가 큰 엔드포인트의 세부 질의(C7)는 임베딩 입력 상한에 잘려 발견되지 않는다. 청크 분할이 적용되지 않는 엔드포인트 문서에서 구조적으로 생기는 실패다.

6. 저장과 색인

별도 검색엔진·벡터 DB를 두지 않는다. 키워드 색인과 벡터 색인이 같은 PostgreSQL 인스턴스, 같은 테이블에 붙어 있어 두 신호가 어긋날 수 없다.

인덱스대상방식쓰이는 곳
ix_chunk_text_tsv chunk.text_tsv — 생성 컬럼 GIN · Postgres FTS keyword arm
ix_chunk_embedding_hnsw chunk.embedding — pgvector HNSW · vector_cosine_ops vector arm
document_meta title / url document_meta.title, .url GIN · gin_trgm_ops (pg_trgm) title arm
01

tsvector는 생성 컬럼

text_tsv를 애플리케이션이 채우지 않고 DB 생성 컬럼으로 둔다. 인서트/업데이트 경로가 늘어도 색인이 빠질 여지가 없다.

02

advisory lock으로 만든 안전한 배치

메타 동기화 · 재색인 · 본문 색인을 서로 다른 주기로 돌리면서도, 새 의존성 없이 Postgres advisory lock만으로 중복 실행과 서로의 기아 상태를 막는다.

03

SQL은 리포지토리 밖으로 안 나간다

<=> 연산자, to_tsquery 같은 Postgres 고유 문법이 전부 리포지토리 안에 갇혀 있어, 검색 로직을 읽을 때 DB 방언을 몰라도 된다.

7. 외부 통합

외부 API는 전부 DocumentSource 프로토콜 뒤에 있다. 구현체 선택은 ProjectSourceResolver가 DB의 project_source 매핑을 읽어 요청마다 다시 하므로, 매핑을 바꿔도 서버 재시작이 필요 없다.

외부 시스템인증가져오는 것파싱
Google Drive API 서비스 계정 토큰 (전역 공유) 프로젝트에 매핑된 폴더의 파일 · 수정 시각 docx · pdf · pptx · xlsx
Notion API integration token (전역 공유) 매핑된 database 행 · 허브 page의 하위 트리를 child_page/child_database로 재귀 탐색 블록 → 평문 (헤딩·리스트 마커 복원)
OpenAPI spec (HTTP) 없음 / 명세 URL 직접 fetch 등록된 source_url의 명세 원문 swagger2 · openapi3 · $ref 해석

Drive/Notion 자격증명은 전역 공유이고 프로젝트마다 달라지는 것은 폴더/DB 매핑뿐이다. 하나의 프로세스·DB가 여러 프로젝트를 함께 서비스하며, 격리는 project 태그로 한다 — 신규 프로젝트 온보딩 비용이 낮은 이유다.

Notion만 통합 난이도가 다르다. Drive는 파일이 폴더에 평탄하게 놓이지만 Notion 문서는 페이지 안에 페이지가, 페이지 안에 데이터베이스가 다시 들어간다. 제목만 긁으면 Notion 자체 검색보다 못한 커버리지가 나오므로, 목록화와 본문 수집 양쪽에서 트리를 따라간다.

01

목록화는 트리 전체를 편다

허브 page든 database 행이든 child_page · child_database를 타고 내려가 하위 문서를 독립 문서로 평탄화한다. 하위 페이지를 품을 수 있는 toggle · column 컨테이너도 통과한다. 무한 순회는 상한으로 끊는다 — 페이지 깊이 MAX_PAGE_DEPTH = 4, 컨테이너 깊이 MAX_CONTAINER_DEPTH = 3(별도로 센다), 총 페이지 MAX_PAGES = 500.

02

본문 재귀는 child_page에서 멈춘다

목록화가 하위 페이지를 이미 독립 문서로 잡으므로, 부모 본문을 모을 때 또 타고 들어가면 같은 텍스트가 두 문서에 중복 색인되고 부모 히트의 스니펫·URL이 실제 출처와 어긋난다. 그래서 본문 수집은 child_page에서 재귀를 끊고 제목만 남긴다 — 부모에서도 하위 문서 이름은 검색된다.

03

블록에 없는 것은 페이지 객체에서

DB 행의 status · formula 같은 속성은 블록이 아니라 페이지 객체에 있어 /blocks/{id}/children만으로는 잡히지 않는다. GET /pages/{id}를 한 번 더 호출해 "{속성명}: {값}" 줄을 본문 앞에 붙인다. 표 셀 · caption · bookmark URL도 같은 이유로 따로 긁는다.

헤딩·리스트 마커를 되살리는 것도 여기 딸린 일이다. Notion 평문에는 서식 정보가 없어 마커 없이 이어 붙이면 markdown_parser가 문서 전체를 "개요" 섹션 하나로 만들고 모든 청크 앵커가 # 개요로 뭉개진다. 블록 타입을 # · - · > 마커로 되돌려 섹션 경계를 복원한다.
