## 0. 결론 먼저 (실험 착수 판단 규율)

1. **가설**: 더 강한 다국어 임베딩 모델은 교차언어 Recall@3(현 50%)을 끌어올린다 — 교차언어 갭은 벡터 arm 자신의 약점이므로 벡터 arm(임베딩)을 바꾸는 정공법.
2. **후보 모델**: 1차 `intfloat/multilingual-e5-base`(현 small과 **동일 계열·드롭인**, dim 384→768), 2차(1차가 유망하나 미달 시에만) `BAAI/bge-m3`(한국어 특화, 단 접두사 규약 다름). 둘 다 로컬 CPU·sentence-transformers·MIT 라이선스(2절).
3. **최우선 선결 과제(docs/13 교훈)**: 현 픽스처의 **교차언어 표본은 8건**뿐이라 Recall@3 해상도가 **12.5pt/건** — "50%→70%"는 사실상 **질의 2건이 뒤집히면 판정이 갈리는 동전 던지기**다. 실험 신뢰를 위해 **교차언어 라벨 질의를 8→20건 이상으로 먼저 보강**하고, 보강 없이는 게이트 수치를 믿지 않는다(4절).
4. **게이트(PASS 조건 4개 AND)**: ①베이스라인이 교차언어 Recall@3 ≈ 50% 재현(하네스 sanity) ②보강셋에서 후보 교차언어 Recall@3 ≥ 70%, **질의별 순위 이동을 눈으로 확인**(진짜 교차언어 브리지지 decoy 노이즈 아님) ③타 카테고리 무회귀 ④임베딩 지연 증가가 예산 내(6절).
5. **프로덕션 무변경**: 실험은 temp-DB + provider/dim 주입으로만. 실제 반영(재색인·컬럼 마이그레이션)은 게이트 통과 후 **별도 착수 지시**로 분리.

## 1. 배경 — 왜 이 실험이고 왜 지금

- docs/12는 "깊이"의 상방을 축1(retrieval recall)·축2(클라 순회)로 나눴고, 축1의 유일한 실측 약점은 **교차언어 Recall@3 50%**(docs/09 P1). 축1을 겨눈 미탐색 레버로 docs/12-B(문맥 청킹)를 지목했으나 **docs/13에서 픽스처 아티팩트로 판명·종결**됐다.
- 남은 축1 미탐색 레버 = **임베딩 모델 자체의 다국어 성능**. docs/11 §5가 "인프라 판단"이라며 명시적으로 스코프 밖에 뒀던 항목이라, retrieval 레버로는 **어느 문서도 판정한 적 없다**(docs/14 §5 신규 판정).
- 리랭킹(docs/12-C)이 교차언어를 못 고치는 이유(정답이 애초에 top-3 풀에 없음 = not-in-pool)와 대조: 임베딩 교체는 **정답을 풀에 넣는 recall 층**을 건드리는 유일한 정공법.

## 2. 후보 모델 확정

현행: `intfloat/multilingual-e5-small` — 384dim, 약 118M params, 다운로드 약 0.47GB, MIT, e5 접두사(`query: `/`passage: `). `app/core/config.py:48` 기본값.

| 후보 | dim | params(약) | 다운로드(약) | 라이선스 | 접두사 규약 | 코드 델타 | 위치 |
|---|---|---|---|---|---|---|---|
| **1차: `intfloat/multilingual-e5-base`** | 768 | 278M | 1.1GB | MIT | e5 동일(`query:`/`passage:`) | **모델명+dim만** (LocalEmbeddingProvider 무변경) | 드롭인. "같은 계열 더 큰 모델" 변수만 격리 |
| 2차(조건부): `BAAI/bge-m3` | 1024 | 568M | 2.2GB | MIT | **다름**(dense는 접두사 없음) | 접두사 우회 필요 | 한국어 특화. 1차가 유망하나 교차언어 잔여 시에만 |
| (참고) `intfloat/multilingual-e5-large` | 1024 | 560M | 2.2GB | MIT | e5 동일 | 모델명+dim만 | e5 계열 최상위. 2차 대안 |

### 2-1. 후보 선정 근거 (단일 변수·최소 델타 우선)

- **1차 e5-base가 정답**: 현 `LocalEmbeddingProvider`가 e5 접두사(`_QUERY_PREFIX`/`_PASSAGE_PREFIX`)를 그대로 쓰므로 **모델명과 dim만 바꾸면 되는 진짜 드롭인**이다. "더 큰 다국어 모델이 교차언어를 닫는가"라는 **단일 변수만** 깨끗이 측정한다.
- **bge-m3는 조건부·나중**: 한국어 성능 평판이 강하지만 (a) dense 임베딩이 **접두사를 안 쓰는 규약**이라 `LocalEmbeddingProvider`에 e5 접두사를 그대로 태우면 오히려 품질이 깨진다 → 실험 하네스에서 이 모델에 한해 접두사를 건너뛰어야 함, (b) 2.2GB·568M로 **CPU 추론이 더 느림**(지연 예산 압박). 따라서 **1차 e5-base가 교차언어를 유의미하게 올리되 70%에 못 미치고 잔여가 한↔영일 때만** 2차로 투입한다. 처음부터 둘 다 돌리지 않는다(불필요한 다운로드·실행 회피).
- e5-large는 e5-base와 같은 드롭인이나 dim·용량이 bge-m3급이라, "한국어 특화"가 필요하면 bge-m3, "e5 계열 최대치"가 필요하면 e5-large — 2차는 둘 중 하나만.

### 2-2. 로컬 CPU 구동 가능성 — 확인

셋 다 `SentenceTransformer(model_name, device="cpu")`로 로드되는 표준 ST 모델이다(현 provider가 이미 이 경로). 신규 패키지 트리 0(sentence-transformers·torch는 이미 의존성). 추가 비용은 **모델 다운로드 용량 + 상주 메모리 + 추론 지연**뿐 — 전부 6절에서 측정 대상.

## 3. 실험 하네스 스펙 (compare_chunking.py 패턴 재사용, 프로덕션 무변경)

`compare_chunking.py`가 확립한 구조 — temp-DB 생성 → 몽키패치로 변형 주입 → rrf 84질의 실행 → 카테고리별 지표 + 교차언어 질의별 순위 이동 → temp-DB drop — 를 그대로 따른다. **바꾸는 변형 축만 "청킹"에서 "임베딩 provider + dim"으로 교체.**

신규 스크립트: `tests/fixtures/rrf_eval/compare_embedding.py`

### 3-1. 변형 주입 방식 (핵심 — 청킹 실험과 다른 유일한 지점)

청킹 실험은 `indexer_service_module.build_chunks`만 몽키패치하면 됐다. 임베딩 교체는 **provider와 벡터 컬럼 dim을 함께** 바꿔야 하고, 여기 **비자명한 마찰이 하나** 있다:

- `ApiChunk.embedding = mapped_column(Vector(EMBEDDING_DIM))`은 **클래스 정의 시점(import)에 dim이 박힌다**(`app/models/openapi.py:333`). `EMBEDDING_DIM=384`. 런타임에 상수만 바꿔도 이미 정의된 컬럼 타입은 안 바뀐다. pgvector는 768 벡터를 `Vector(384)` 컬럼에 넣으면 에러.
- 게다가 `app/composition.py:109`가 `provider.dim == EMBEDDING_DIM`을 assert한다.

**해결(developer가 택1, 실험 스크립트 한정 — 프로덕션 코드 무변경)**:
- **(권장) 모델별 서브프로세스 격리**: 스크립트가 후보 모델마다 **자식 프로세스**를 띄우고, 그 프로세스가 ORM import **전에** `EMBEDDING_DIM`을 후보 dim으로 설정(예: 환경변수 → `openapi.py`가 읽도록 실험용 shim, 또는 import 순서 제어). 각 프로세스는 자기 dim으로 컬럼을 만들고 자기 모델로 색인·평가 → 결과(ranks)를 부모로 반환. dim이 import 타임에 박히는 문제를 프로세스 경계로 회피하는 가장 깨끗한 방법.
- **(대안) in-process 컬럼 타입 오버라이드**: `create_all` 직전에 `ApiChunk.__table__.c.embedding.type = Vector(candidate_dim)`로 교체하고 `EMBEDDING_DIM`도 패치, composition assert는 실험 스크립트가 provider를 직접 배선(build_services 우회)해 회피. 더 적은 프로세스지만 ORM 내부 상태를 만지므로 검증 부담이 큼.
- 어느 쪽이든 **착수 전 검증 필수**: "candidate provider.dim == 실제 생성된 벡터 컬럼 dim"을 스크립트가 assert로 못박아, dim 불일치로 인한 조용한 오색인을 차단한다.

### 3-2. provider 주입

- `AppState.from_engine(...)`가 provider를 어떻게 잡는지에 맞춰, 실험 스크립트는 `LocalEmbeddingProvider(model_name=<candidate>)`를 명시적으로 배선한다(현 `composition._build_embedding_provider` 경로가 `settings.embedding_model`을 읽으므로, 스크립트가 settings를 후보 모델명으로 주거나 provider를 직접 주입).
- bge-m3를 돌릴 경우(2차), 그 모델에 한해 **e5 접두사를 건너뛰는** provider 변형을 실험 스크립트 안에 둔다(프로덕션 provider 무변경).

### 3-3. 실행 축 (변형 목록)

1. **baseline**: `multilingual-e5-small`(384) — 현행 재현.
2. **후보1**: `multilingual-e5-base`(768).
3. (조건부) **후보2**: `bge-m3`(1024, 접두사 우회) — 후보1 결과 보고 lead 판단 후에만.

각 축은 동일 84(또는 보강된) 질의셋·동일 rrf 전략·동일 temp-DB 절차로 실행. 청킹은 baseline 고정(이 실험의 변수는 임베딩뿐).

### 3-4. 출력 (compare_chunking.py 출력 형식 재사용)

- 전체 지표(Recall@{1,3,5,10}·MRR·nDCG@10) baseline vs 후보.
- **카테고리별 분해** — 교차언어 카테고리를 최우선으로 읽는다.
- **교차언어 질의별 순위 이동 표**(baseline 순위 → 후보 순위 → 개선/무변/악화) — docs/13 교훈대로 **어느 질의가 왜 움직였는지 사람이 검수**할 수 있게.
- 타 카테고리 회귀 목록.

## 4. 픽스처 표본 적정성 — 선결 점검 + 보강 (docs/13 교훈의 핵심 적용)

### 4-1. 현 표본의 한계 (실측 확인)

- 픽스처는 **엔드포인트 20개·문서 1개**. 이중언어 구조: **`/users` 계열 5개(POST·GET·GET/{id}·PATCH·DELETE)만 영문 summary/description**, 나머지 15개는 한글. 이 구조가 "한글질의↔영문문서" 교차언어 조건을 만든다.
- 교차언어 카테고리 = **8건**(queries.json 41~48행): 한글질의→영문 `/users` 4건 + 영문질의→한글문서 4건(products·health·invoices).
- **문제**: 8건에서 Recall@3 해상도 = **12.5pt/건**. 50%(4/8)→70%(≥6/8)은 **질의 2건 뒤집힘**에 걸린다. 게다가 한글→영문 방향 신호가 **`/users` 5개 엔드포인트에만** 얹혀 있어, 소수 엔드포인트·소수 질의에 판정이 과의존한다. docs/13이 경고한 "작은 픽스처에서 나온 개선이 진짜인가" 함정에 정확히 노출.

### 4-2. 보강 방안 (게이트 신뢰의 전제 — 실험 전 수행)

**교차언어 라벨 질의를 8 → 20건 이상으로 확장**한다(해상도 12.5pt → ~5pt/건, 판정이 2건 동전던지기에서 벗어남).

- **양방향 균형**: 한글질의→영문 `/users` 문서 방향, 영문질의→한글문서 방향을 고루 늘린다. 현 픽스처의 이중언어 구조가 이미 이를 지원하므로 **라벨 질의 추가만으로 가능**(픽스처 openapi.json 재설계 불필요가 1차 목표).
- **표현 다양화**: 같은 엔드포인트에 대해 어휘·구문이 다른 교차언어 질의를 복수 배치(예: `/users` GET에 "유저 리스트 조회", "가입된 회원 전부", "회원 명단" 등) — 단일 표현 우연 매칭이 판정을 흔들지 않도록.
- **엔드포인트 커버리지 점검**: 20건이 여전히 `/users` 5개에만 몰리면(한글→영문 방향 surface 부족), 그때만 **영문 summary 엔드포인트를 픽스처에 2~3개 추가**해 교차언어 surface를 넓힌다. 라벨 추가로 충분하면 픽스처는 건드리지 않는다(YAGNI, 픽스처 변경은 baseline 재현치도 흔들므로 최소화).
- 보강 질의에는 category를 교차언어로 명확히 태깅(스크립트의 카테고리 분해가 자동 집계).

### 4-3. 아티팩트 방어 (docs/13 재발 방지)

- **baseline sanity 우선**: 보강셋으로 먼저 baseline(e5-small)을 돌려 교차언어 Recall@3가 여전히 ~50% 근방인지 확인. 크게 어긋나면(예: 보강 질의가 너무 쉬워 baseline이 이미 80%) 보강셋이 문제를 과소재현하는 것 → 질의 난이도 재조정 후 재측정. **baseline이 문제를 제대로 재현해야 개선 측정이 의미**를 갖는다.
- **질의별 검수 의무화**: 후보가 올린 교차언어 질의를 한 건씩 봐서, 실제로 "한글질의가 영문 문서를 찾아냈는가" 같은 **진짜 브리지**인지, 아니면 decoy 우연·토큰 겹침인지 확인. 숫자만 보고 통과시키지 않는다 — 이게 docs/13에서 놓쳤던 지점.

## 5. 실험 절차 (developer 실행 순서)

1. **보강**: `queries.json`에 교차언어 라벨 질의 추가(8→20+, 4-2). 필요 시에만 픽스처에 영문 엔드포인트 소수 추가. `_validate_labels`로 라벨 무결성 확인.
2. **하네스 작성**: `compare_embedding.py`(3절). dim/provider 주입 방식 확정(3-1 권장=서브프로세스 격리), "provider.dim == 컬럼 dim" assert 못박기.
3. **baseline sanity**: e5-small로 보강셋 실행 → 교차언어 Recall@3 ≈ 50% 재현 확인(4-3). 어긋나면 보강셋 조정 후 반복.
4. **후보1 실행**: e5-base(768) 색인·평가. 전체·카테고리·교차언어 질의별 이동 출력.

6. **지연 측정**(6절)을 각 후보 실행에 포함.
7. **결과를 docs/15에 실측 절로 추가**(docs/13 형식) — baseline/후보 지표표 + 교차언어 질의별 이동 + 지연 + 판정.

## 5-확정. architect 최종 판정 (2026-08-12) — HOLD 확정, bge-m3 미착수

게이트 설계자로서 lead의 1차 판단(HOLD 쪽)을 **확정**한다. **e5-small 유지, 2차(bge-m3) 착수 안 함.**

### 왜 bge-m3를 돌리지 않는가 — 후보 공간이 소진됐다

게이트는 4조건 **AND**이고, 구속 조건은 **G4(지연)**다. e5-base가 이미 p95 7.02x로 예산(3x)의 2배 넘게 초과했다. 여기서 핵심은 **G4와 G2가 모델 크기에 대해 반대 방향**이라는 점이다:

- **G2(교차언어 recall)를 더 올리려면 → 더 크고 강한 다국어 모델**이 필요하다(e5-small→base에서 확인된 방향).
- **G4(지연)를 통과하려면 → 더 작은/가벼운 모델**이 필요하다(CPU 추론이 검색 지연 지배 비용, docs/11 B1).

bge-m3는 568M으로 e5-base(278M)의 2배·e5-small(118M)의 ~5배다. **G2는 더 올릴 수 있어도 G4는 e5-base보다 확정적으로 더 악화**한다(§2-1에 "CPU 추론이 더 느림" 명시). 즉 bge-m3가 G2 70%를 넘겨도 **G4에서 e5-base보다 더 크게 실패**해 4조건 AND를 통과할 길이 없다. **CPU 임베딩이라는 제약 위에서는 G2와 G4를 동시에 만족하는 모델이 존재하지 않는다** — 후보 공간이 소진됐다. bge-m3 실행은 결과가 이미 정해진(G4 확정 실패) 밑지는 지출이다.

### 이건 죽은 레버가 아니라 "실재하나 지금은 감당 불가"인 레버

docs/13(문맥 청킹)은 **개선 자체가 픽스처 아티팩트로 가짜**여서 소멸했다. 이번은 다르다 — 교차언어 12→16건(+4), `PATCH`/`DELETE /users/{userId}` 순위 10→1·8→1은 **사람 검수로 확인된 진짜 의미 브리지**다(§5-실측). 가설(더 강한 다국어 임베딩이 교차언어를 올린다)은 **부분 확증**됐다. 따라서 판정은 "레버가 안 통한다"가 아니라 **"레버는 통하나 CPU 추론 비용(4.5~7x) 때문에 지금 채택이 밑진다"**이다. 이 구분이 재검토 트리거의 성격을 정한다.

### 재검토 트리거 (정정·구체화)

developer가 남긴 트리거를 게이트 설계자 관점에서 정정·보강한다:

1. **S1 병렬화는 약한 트리거다(정정)**: S1은 총지연을 `max(embed_infer, keyword_db) + vector_db`로 만든다. 그런데 임베딩 추론은 e5-small에서도 **이미 지배 항**이고 e5-base에서 4.5x로 더 커진다 — `embed_infer ≫ keyword_db`이므로 S1로 겹쳐도 embed가 여전히 지배해 4.5x를 흡수하지 못한다. **S1 완료가 곧 e5-base 재실행 정당화로 이어지지 않는다.** S1은 지연 최적화로 가치가 있으나 이 게이트를 여는 열쇠는 아니다.
2. **더 옳은 다음 수 = e5-base 양자화/ONNX(int8) 추론(신규, 지금 스코프 밖)**: G4만이 유일 블로커이고 G2는 66.7%로 이미 근접했으므로, **recall(66.7%)을 유지한 채 지연만 깎는** 경로가 정공법이다. bge-m3(지연 악화)보다 이쪽이 옳다. int8 양자화/ONNX Runtime으로 e5-base p95를 3x 이내로 끌어내릴 수 있는지가 **다음 실험 후보** — 단 별도 설계·착수 지시 건이며 지금 열지 않는다.
3. **실사용 한→영 end-to-end 실패 관측 시**: 반환된 후보 안에 정답이 아예 없어(not-in-pool) 클라 LLM이 `/users` 계열을 못 찾는 사례가 실제로 관측되면 우선순위를 재평가한다(리랭킹 HOLD, docs/09 P3·docs/12-C와 동일 격의 트리거 — 서버 지표가 아니라 실사용 실패).
4. **하드웨어 변경(GPU 등)**: CPU 추론 제약이 풀리면 G4 저울이 근본적으로 바뀐다 — 그때 e5-base/bge-m3 재평가.

### 잔여 7건(한→영 `/users`)은 무대책이 아니다

게이트 미달로 임베딩 교체는 보류하지만, 이 잔여가 정확히 겨눠지는 **무비용 현존 레버가 이미 배포**돼 있다 — `query_variants`(docs/12-A, 커밋 `c91cedb`). 클라가 한글 질의의 영문 variant("회원 명단"→"user list" 등)를 넘기면 **키워드 arm이 영문 `/users` 문서를 직접** 친다(임베딩 브리지 없이 어휘 일치로). 한→영 방향은 임베딩 교체 없이도 클라 위임으로 보강 가능한 경로가 살아 있다.

### 결론

**HOLD 확정 — e5-small 유지. bge-m3 미착수. 이 실험 라인 종결**(docs/13 옵션B 종결과 동일 격). 재개 조건은 위 트리거 2·3·4(특히 2: e5-base 양자화 실험) 중 하나가 성립할 때다.

- **설정**: `app/core/config.py`의 `embedding_model` 기본값 교체, `composition` dim assert 자동 정합.
- **비용 성격**: 전면 재색인은 1회성이나 규모 있음 — 게이트 통과(실측 이득 확인)가 이 비용의 전제.

> 핵심: 이 실험은 **temp-DB에서 dim/provider만 갈아끼워 교차언어 이득과 지연 대가를 실측**하는 것이다. docs/13의 함정(작은 픽스처의 가짜 개선)을 피하는 장치가 이 설계의 절반 — **표본 보강(8→20+)과 질의별 검수·baseline sanity**가 없으면 어떤 숫자도 믿지 않는다.
