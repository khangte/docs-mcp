## 0. 결론 먼저

- **실험은 돌릴 가치가 있다** — 단, "효과가 클 것 같아서"가 아니라 **비용이 거의 0이고**
  (기존 하네스 재사용 + 프로덕션 무변경 + 재사용 A/B 하네스가 부산물로 남음), **유일한 미탐색
  리트리벌 레버를 실측으로 닫기 위해서**다. `docs/12`가 "P1 평가셋으로 먼저 실측 후 착수"로 건 게이트가
  바로 이 실험이다.
- **단, 기대효과에 대한 architect의 사전 판단은 낮다.** 교차언어 약점은 **문맥 부족이 아니라 표현
  (짧은 기술 문자열에 대한 e5 교차언어 정렬) 문제**이고, 문맥 청킹이 얹는 상위 문맥은 **자식과 같은
  언어**라 교차언어 다리를 새로 놓지 못한다(§3 상세). 그래서 이 실험의 진짜 값은 "개선 기대"보다
  **"안 되는 것을 싸게 확정"**에 가깝다(P2·P4가 실측으로 닫힌 것과 동일 논리).
- **실행 주체**: 실험은 코드 작성(변형 청커 + 하네스) + 로컬 postgres + 임베딩 모델 로딩이 필요 →
  **developer 위임**. architect는 아래 실험 스펙(변형 청크 텍스트·몽키패치 지점·지표·게이트)을 완비했고,
  developer는 이를 기계적으로 실행하면 된다.
- **두 방향 중 실험 대상은 방향 1(문맥 증강)만.** 방향 2(부모-자식 분리색인)는 현 코퍼스(단일 문서·
  부모 1개)에서 무의미하고 검색 형태(엔드포인트→엔드포인트)와 안 맞으며 "서버 판단" 원칙에 스친다(§2.2).

## 1. 현 청킹 구조 (실험의 출발점)

`chunk_builder.build_endpoint_chunk_text(endpoint)` — **순수 함수**, `ParsedEndpoint` 하나만 받아
단일 블롭을 만든다:

```
[GET] /products — 상품 목록
상품 카탈로그를 조회한다
Tags: products
Params: limit(query,optional), ...
Responses: 200
```

- 이 `text` 한 덩어리가 **FTS `text_tsv`(키워드 arm)와 임베딩(벡터 arm) 양쪽 입력**이다
  (`indexer_service.py:103~112`). → 청크 텍스트만 바꾸면 **두 arm이 동시에** 바뀐다.
- 상위 문맥(문서 `info.title`, 태그, 인접 엔드포인트)은 **현재 청크에 안 들어간다**. 단,
  **path·tag의 영문 토큰은 이미 블롭에 있다**(`/products`, `Tags: products`) — 이게 §3 판단의 핵심.

## 2. 청킹 전략 후보 두 방향

### 방향 1 — 문맥 증강(contextual augmentation) — ✅ 실험 대상

자식(엔드포인트) 청크는 그대로 두되, **상위 문맥을 청크 텍스트 앞에 얹는다.**

```
API: 평가용 통합 API            ← document.title
Tag: products                   ← 대표 태그(+태그 설명이 있으면 함께)
[GET] /products — 상품 목록
상품 카탈로그를 조회한다
Tags: products
Params: ...
Responses: ...
```

- **장점**: 변경 표면이 `chunk_builder` 텍스트 한 곳. 새 청크 타입/스키마/관계 없음 →
  **재색인만**(마이그레이션 불필요). 검색은 여전히 엔드포인트→엔드포인트라 **2단계 분리 유지**.
  두 arm 동시 수혜.
- **단점/리스크**:
  - **자기 신호 희석** — 텍스트가 길어지면 임베딩이 더 많은 토큰을 평균 → 엔드포인트 고유 신호가
    묽어져 **precision/top-1을 오히려 떨어뜨릴 수 있다**(양날). 모든 형제가 같은 doc/tag 접두사를
    공유하면 FTS 필드 희석·형제 간 변별력 저하도 가능.
  - **교차언어 다리 부재** — 상위 문맥은 자식과 같은 언어(§3).
  - e5 입력 길이(≈512토큰)는 이 규모에서 제약 아님.
- **변형 축(실험에서 함께 볼 수 있는 소변형)**: (a) doc title만, (b) doc title + tag,
  (c) + 인접 형제 summary 몇 개. 우선 (b)를 기준안으로, 여유 있으면 (a)/(c)도.

### 방향 2 — 부모-자식 계층 분리색인 — ⏸ 이번 실험 제외(권장)

부모(문서/태그) 청크와 자식(엔드포인트) 청크를 **별도 색인**하고, 검색 시 둘을 조회해
병합(자식 점수 + 부모매칭 부스트, 또는 부모 히트→자식 확장)한다.

- **제외 사유**:
  1. **현 코퍼스에서 무의미** — 픽스처는 단일 문서(부모 1개). 부모 색인이 변별에 기여할 게 없다.
  2. **검색 형태 불일치** — 엔드포인트 검색은 엔드포인트 후보를 반환한다. 부모 히트를 자식으로
     환원하려면 **검색 시점 병합 로직**이 필요한데, 이는 "부모/자식을 어떻게 합칠지 **서버가 판단**"
     = `docs/09`·`docs/11` 원칙(판단은 클라)에 스친다.
  3. **규모** — 새 청크 관계·스키마·병합 코드 → 단순 재색인을 넘는 작업. 방향 1이 실패하면
     이건 더더욱 근거가 없다.
- **재검토 조건**: 실제 다문서(문서 수십+, 문서별 상이한 도메인) 코퍼스가 생기고, 방향 1의 문맥
  증강이 유의미했을 때. 그전엔 YAGNI.

## 3. 이 실험이 겨냥할 지표 + architect의 사전 판단

- **주 지표**: `queries.json` **교차언어 카테고리 8질의**의 Recall@3 / MRR (rrf 전략 고정, 프로덕션
  기본값). `docs/09` P1이 이 카테고리를 50%로 실측 → 유일 약점.
- **회귀 감시**: 전 카테고리 Recall@3/MRR을 함께 출력해 **다른 카테고리 회귀**(특히 이미 강한
  동의어·필드희석·경로) 여부 확인. 방향 1의 "자기 신호 희석" 리스크가 여기서 드러난다.
- **해상도 주의(중요)**: 교차언어는 **8질의뿐** → **1질의 = Recall@3 12.5pt**. 통계적으로 얇다.
  1건 이동을 "효과"로 오독하지 말 것.

### architect 사전 판단(왜 기대가 낮은가)

교차언어 질의 예: `list all products`(영문)→`GET /products`(한글문서), `새 사용자 등록`(한글)→
`POST /users`(영문문서). 실패 원인은 **e5가 짧은 기술 문자열의 한↔영 의미공간을 못 붙이는 표현
문제**다. 문맥 증강이 얹는 것은:

- **doc title / tag / 인접 설명 = 자식과 같은 언어** → 새 교차언어 신호 아님.
- **path·tag의 영문 토큰은 이미 블롭에 존재** → 추가 영문 신호도 아님.

→ 즉 문맥 증강은 **"문맥이 없어서 못 찾는" 실패에는 듣지만, 교차언어는 그 성격이 아니다.**
유일하게 그럴듯한 기전은 **한글 doc title이 영문 엔드포인트 청크에 섞여 한글질의→영문문서를
구해주는 것**인데, 이는 **픽스처 아티팩트**(단일 한글 title이 전 청크에 번지는 것)일 뿐 일반화되는
기전이 아니다. 결과 해석 시 이 점을 반드시 감안.

## 4. 실험 설계 (소규모, 프로덕션 무변경) — developer 실행용 스펙

기존 `tests/fixtures/rrf_eval/` 하네스를 **거의 그대로 재사용**한다. 신규 스크립트 1개.

### 4.1. 실행 방식

- 신규 파일: `tests/fixtures/rrf_eval/compare_chunking.py`(또는 `rag_context_eval/`).
  `compare_strategies.py`의 임시 DB 생성/등록/지표/카테고리 분해 로직을 재사용(임포트 또는 복제).
- **청킹 스왑(프로덕션 무변경 핵심)**: `indexer_service`가 `from ...chunk_builder import build_chunks`로
  바인딩하므로, 실험 스크립트에서 **`indexer_service.build_chunks`를 문맥 증강 변형으로 몽키패치**한다.
  변형은 `build_chunks`를 미러링하되 엔드포인트 청크 텍스트에 `document.title`(+대표 tag)을 접두로 얹는다.
  프로덕션 파일은 **한 줄도 수정하지 않는다.**
- **비교 축**: 전략은 `rrf` 하나로 고정하고, **청킹만** baseline vs 문맥증강(방향 1)로 A/B.
  (전략 축은 이미 `docs/09`에서 닫힘 — 여기선 청킹만 변수.)
- **출력**: 전체 + 카테고리별 Recall@{1,3,5,10}/MRR/nDCG@10, 그리고 **질의 단위 순위 이동표**
  (교차언어 8건은 개별 before/after 명시).

### 4.2. 절차

1. 임시 DB 생성(기존 `_make_temp_db`) → `openapi.json` 등록(baseline 청킹).
2. 84질의 rrf 실행 → 지표/카테고리 기록.
3. 임시 DB 재생성 → **몽키패치된 문맥증강 청킹**으로 재등록 → 동일 84질의 rrf 실행.
4. 두 실측 델타 출력. 교차언어 카테고리와 회귀를 강조.
5. 임시 DB 삭제.

### 4.3. 비용

- 코드: 신규 ~100줄(하네스 재사용). 마이그레이션·스키마·프로덕션 변경 0.
- 런타임: 모델 로딩 + (20엔드포인트 × 2변형 임베딩) + (84질의 × 2). **수 분.** 로컬 postgres 필요
  (`docker compose up -d postgres`) — compare_strategies와 동일 전제.
- 리스크: 실험 자체는 임시 DB에서만 → 프로덕션 리스크 0.

## 5. 판정 게이트 (실험 후 착수 여부)

실험 결과를 아래 기준으로 lead에 재보고하고, **프로덕션 재색인 착수 여부는 그때 판단**한다.

| 결과 | 판정 |
|---|---|
| 교차언어 Recall@3 **+2질의 이상**(≥+25pt) 개선 **AND 타 카테고리 회귀 0** | 프로덕션 재색인 착수 검토 대상으로 승격 |
| 교차언어 +1질의(+12.5pt)만, 또는 타 카테고리 경미 회귀 동반 | **시그널 불충분** — 8질의 해상도 한계. 대규모 평가셋 생길 때로 보류 |
| 교차언어 무변/악화, 또는 top-1·타 카테고리 회귀 | **옵션 B 종결**("측정, 효과 없음" — P2/P4와 동일 처리) |

- 8질의 해상도가 얇아 **+1질의는 착수 근거로 부족**하다(전면 재색인 비용 대비). 최소 +2질의를 실질
  시그널로 본다.
- 방향 1이 유의미하면, 그다음에야 방향 2(분리색인)를 대규모 코퍼스 전제로 재론한다.

## 5-실측. 실험 결과 및 최종 판정 (2026-08-12, developer 실행 · architect 판정)

`compare_chunking.py`(방향1, 접두 `API: {title}` + `Tag: {tag}`) 84질의 rrf A/B 실측.

### 결과 요지
- **교차언어(8건)**: Recall@3 50%→88%(**+3질의**, 게이트 +2 초과), Recall@5 50%→100%, MRR 0.416→0.677.
- **전체(84질의)**: Recall@3 88%→99%, MRR 0.758→0.848 — 전 지표 개선.
- **회귀 4건, 전부 top-1만 밀림**(1→2/3): 인증해줘(로그인) 1→3, 환불 1→2, user info·order info 1→2.
  **회귀가 난 모든 카테고리의 Recall@3/5/10은 100% 유지** — 정답이 top-3 밖으로 나간 건 0건.

### 게이트 문구 정정 (핵심)
docs/13 §5 3행의 "**top-1 회귀 → 종결**" 절은 이 프로젝트의 확립 원칙(`docs/09` P3 HOLD:
"이 도구는 후보 피더, 구속 지표는 top-1이 아니라 recall@k")과 **모순**이다. 후보 풀 안 순위 뒤섞임
(1→2/3)은 클라 LLM이 이미 top_k를 읽고 재선택하므로 구속 지표의 회귀가 아니다. 따라서 게이트는
**recall@k 회귀 기준으로 읽는다** → 이 실측은 recall@k 회귀 0. 문자 그대로의 "종결"은 적용하지 않는다.

### 그럼에도 프로덕션 착수는 보류 — 이득이 픽스처 아티팩트로 확인됨
개선 4건은 **전부 한글질의 → 영문문서(`/users` 계열)**, 무변 4건은 **전부 영문질의 → 한글문서**.
즉 유일한 한글 doc title(`평가용 통합 API`)이 영문 청크에 섞여 한글질의를 끌어준 것 —
**docs/13 §3에서 사전 등록한 "픽스처 아티팩트" 기전 그대로**다. 역방향(영문질의→한글문서) 이득은 0.
실제 다문서 코퍼스(문서별 title이 단일 언어, 문서 다수)에선 이 한글-title 번짐이 재현되지 않아
**일반화 근거가 약하다.** 더해 흔한토큰·패러프레이즈에서 예측한 "자기 신호 희석"(top-1 하락)이
실제로 관측됐고, 형제가 doc/tag 접두를 공유할수록 규모에서 악화할 소지가 있다.

### 1차 판정(title+tag): 조건부 보류 → tag-only 후속으로 분기 해소
title+tag는 recall@k 회귀 0이라 종결은 아니었으나, 이득이 픽스처 title 번짐에 국한돼 즉시 승격도
불가 → `Tag`만 남기고 `API: {title}`을 뺀 **tag-only 변형**으로 (a)이득 생존=일반화 기전 존재→승격,
(b)이득 소멸=순수 아티팩트→종결을 가르기로 했다.

### tag-only 후속 실측 + 노이즈 검증 (2026-08-12, developer 실행 · architect 재실행 확인)
- **교차언어 Recall@3 이득 +3 → +0 소멸.** title 제거 즉시 title+tag의 개선이 사라짐 → **(b) 순수
  아티팩트 확정.** top-1 희석도 완화 안 됨(tag-only도 흔한토큰 R@1 하락 지속, 타카테고리 회귀 다수).
- **baseline 노이즈(63%↔68%) 판정 영향 검증 — 없음.** architect가 tag-only를 2회 재실행:
  - 결정 지표(교차언어 Recall@3): 2회 모두 baseline 4/8 → tag-only 4/8, **delta +0 (분산 0).**
  - 노이즈의 실제 위치: 전체 R@1은 2회 모두 68%로 안정. 흔들린 건 **변형의 top-1·MRR**(변형 R@1
    61%↔63%, 교차언어 top-1 50%↔25%, MRR 0.54↔0.42) — RRF 동점 순위가 1↔2로 뒤집히는 축이다.
    즉 노이즈는 **top-1/MRR(비구속 지표)에만** 살고 **교차언어 Recall@3(구속 지표)은 안 움직인다.**
  - 결론: title+tag의 +3과 tag-only의 +0 격차(3질의)는 관측된 Recall@3 분산(0질의)을 압도 →
    노이즈로 설명 불가. developer가 본 baseline 63→68 드리프트는 top-1 동점처리 지터(1~2질의)로
    구속 지표와 무관. **판정에 영향 없음.**

### 최종 판정: **옵션 B 종결 (measured, no generalizable effect)**
- title+tag의 교차언어 이득은 **유일한 한글 doc title이 영문 청크에 번진 픽스처 아티팩트**임이
  tag-only 대조로 인과 확정(title 빼면 이득 소멸). 일반화 기전 없음.
- 남는 것은 **자기 신호 희석(top-1 하락)이라는 손해뿐** — 두 변형 다 관측.
- recall@k 기준 손해는 없으나(구속 지표 회귀 0) **얻는 것도 없음** → 전면 재색인 비용을 정당화 못 함.
  `docs/09` P2·P4가 "측정 후 효과 없어 보류/유지"로 닫힌 것과 동일 처리.
- 방향 2(부모-자식 분리색인)는 §2.2대로 현 코퍼스에서 무의미 → 함께 미착수.
- **재개 트리거**: 실제 다문서(문서 다수·문서별 단일언어 title) 코퍼스가 생겨 교차언어가 실사용
  걸림돌로 재관측될 때. 그때는 문맥 청킹이 아니라 **retrieval 자체**(교차언어 임베딩·질의처리)를
  겨눈다(`docs/09` P3 재검토 트리거와 동일 방향).

## 6. 한 줄 요약

옵션 B의 유일한 실험 대상은 **방향 1(문맥 증강)** — 기존 rrf 하네스에 청킹만 A/B로 갈아끼우는
**프로덕션 무변경 소규모 실측**이다. architect 사전 판단으로 교차언어(표현 문제)에 문맥 증강(같은 언어)이
들을 기대는 낮으나, **실험 비용이 거의 0이라 "안 되는 것을 싸게 확정"하는 값**이 있어 **developer 위임
실행을 권장**한다. 착수는 **교차언어 +2질의·회귀 0** 게이트 통과 시에만.
