# 45. 포트폴리오 문서 리뷰 판정 — 헤드라인 지표 반증분 반영, 타입 전용 임포트 강제

- 작성: architect
- 리뷰 출처: reviewer (`docs/architecture-overview.html`, `docs/architecture-detailed.html`)
- 판정: **2건 모두 지적 타당 — 전부 수용**
  - (1) 헤드라인 지표: **문서 수정**(architect 직접 반영 완료)
  - (2) 런타임 임포트: **코드 수정 + 문서 표현 정정**(developer 지시)

## 1. 지적 1 — 반증된 지표를 대외 헤드라인에 노출

### 1.1 사실 확인

reviewer 지적대로다. 두 문서의 헤드라인 통계는 `09-search-quality-post-rrf.md`
(2026-08-10~12, **합성 하네스 20 엔드포인트**, n=20) 값이었다.

| 출처 | 코퍼스 | Recall@1 | Recall@3 | Recall@10 | MRR |
|---|---|---|---|---|---|
| doc/09 (합성) | 엔드포인트 20개 | 68% | **88%** | **95%** | 0.788 |
| doc/29 §1 (실 코퍼스, stale) | Stripe 589 + GitHub 1220 | 10% | 30% | 45% | 0.200 |
| doc/29 §13.1 (실 코퍼스, **마감 재측정**) | 동일 | 15% | **25%** | **50%** | 0.248 |

doc/29 §1 본문이 직접 명시한다 — "synthetic 20-엔드포인트 하네스 대비 큰 폭 하락 …
589~1220개 규모 실 코퍼스에서 지표가 포화되지 않고 실제 변별력을 보인다."

즉 88/95%는 **성능 수치가 아니라 벤치마크가 포화됐다는 증거**였고, 그 사실을 이 저장소가
스스로 하루 뒤에 측정해 남겨 두었다. 그걸 대외 문서 첫 화면에 그대로 걸어 둔 것은
방어할 수 없다.

reviewer가 §1(20~30% / 40~50%)을 인용했는데, §1은 문서 본문에 `stale` 표시가 붙어 있고
마감값은 §13.1이다. 결론은 바뀌지 않는다 — 어느 쪽을 쓰든 헤드라인 88/95%는 반증됐다.
**수치를 반영할 때는 §13.1(마감 재측정)을 쓴다.**

### 1.2 판정 — "실코퍼스값 교체 / caveat 병기 / 스탯 제거" 중 무엇인가

셋 다 부분적으로만 맞다. 채택안은 **문서별로 다르게** 간다.

**`architecture-detailed.html` — 교체 + 전용 섹션 신설.**
헤드라인 타일에서 품질 수치를 빼고 `1,809 평가 코퍼스 엔드포인트`(589 + 1,220)로 바꿨다.
대신 **§5 "검색 품질 측정"** 섹션을 새로 만들어 합성값과 실 코퍼스값을 **같은 표에 나란히**
싣고, n=20 표준오차(±11%p대)와 무너지는 축(C2 교차언어, C7 512토큰 상한)까지 적었다.

단일 숫자를 caveat와 함께 타일에 욱여넣는 방식은 택하지 않았다. 타일은 맥락을 담을 자리가
아니라서, caveat가 붙는 순간 읽는 사람은 숫자만 가져가고 각주는 버린다.

**`architecture-overview.html` — 제거 + 유도.**
발표용이라 지표를 놓을 자리가 없다. `88% 상위 3건 안에 정답` 타일을
`1,809 실제 API로 검증한 규모`로 바꾸고, 상단 링크에 "검색 품질 측정값 → 02" 를 넣었다.
이 문서의 나머지 문구는 정확도를 주장하지 않으므로(카드 3장은 역할 분리·통합 창구·자동
동기화 이야기다) 수치 제거만으로 과장이 남지 않는다.

### 1.3 왜 이렇게 쓰는 편이 유리한가

포트폴리오 관점에서도 이쪽이 강하다. "88%를 달성했다"는 튜닝 자랑이고, 실제로 한 일은
**자기 벤치를 의심해 실 코퍼스 평가 하네스를 만들고(핀 SHA 프리즈, 재현 커맨드 1줄),
자기 수치를 반증하고, 실패 축을 카테고리로 분해해 남긴 것**이다. 후자가 훨씬 드문 신호다.
§5를 "성능 자랑" 대신 "측정 방법론과 발견" 절로 구성한 이유다.

### 1.4 반영 완료 내역

| 파일 | 변경 |
|---|---|
| `02` stat 타일 | `88 / 95%` → `1,809` (평가 코퍼스 엔드포인트) |
| `02` §5 신설 | 합성 vs 실 코퍼스 비교표 + n=20 caveat + 발견 카드 3장(벤치 포화·C2 교차언어·C7 토큰 상한) |
| `02` §6~§8 | 기존 저장/색인·외부 통합·기술 스택 번호 재조정 |
| `01` stat 타일 | `88%` → `1,809` (실제 API로 검증한 규모) |
| `01` 상단 링크 | "검색 품질 측정값" 항목 추가 |

## 2. 지적 2 — `TYPE_CHECKING` 가드 없는 런타임 임포트

### 2.1 사실 확인

reviewer 지적이 맞다. `app/services/documents/registered_resync.py:21` 은 평범한 런타임
임포트다. 반면 문서 인셋은 "타입 전용 역참조 / 런타임 결합이 없다"고 적었다.

doc/44 §2-b에서 내가 쓴 근거 자체는 정확했다 — `app/mcp/types.py` 는 `typing` 만
임포트하는 leaf 모듈이라 이걸 끌어와도 `fastmcp` 가 딸려오지 않는다. 하지만 **다이어그램의
짧은 라벨로 압축되면서** "임포트가 런타임에 일어나지 않는다"로 읽히게 됐다. 압축이 만든
과장이고, 문서 잘못이다.

### 2.2 판정 — 코드를 고친다 (문서만 완화하지 않는다)

두 선택지 중 **코드 수정**을 택한다.

- 안전성은 확인됐다. 파일에 `from __future__ import annotations` 가 이미 있고,
  `RegisteredResyncResult` 는 **35행 반환 애너테이션에서만** 쓰인다(파일 내 등장은
  docstring·import·애너테이션 3곳뿐). 반환문은 dict 리터럴이라 런타임 생성자 호출이 없다.
- 가드를 씌우면 문서의 주장이 **근사적으로 참**에서 **문자 그대로 참**이 된다. 이 저장소에
  단 하나 남은 계층 예외라 그 한 건의 성격은 정확히 적히는 편이 낫다.
- 문서만 완화하는 안은 "지금은 무해하다"는 서술로 남는데, 그건 앞으로도 무해하다는 보장이
  아니다. 가드는 이 결합이 값 수준으로 번지면 즉시 실패하게 만든다 — 문장이 아니라 강제다.

3줄짜리 변경이고 호출부·테스트 영향이 없다. 여기서 "그냥 문구를 낮추자"는 것은
게으름이 아니라 부채다.

### 2.3 developer 지시

`app/services/documents/registered_resync.py` 만 수정한다.

```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from app.mcp.types import RegisteredResyncResult
```

- 기존 `from app.mcp.types import RegisteredResyncResult`(21행) 를 위 형태로 옮긴다.
- 모듈 docstring 의 유지 근거 문장에 "`TYPE_CHECKING` 가드로 런타임 임포트는 없다"를
  더한다(기존 doc/44 §2-b 참조는 유지).
- 호출부·테스트 변경 없음. `app/mcp/tools/sources.py`, `app/scripts/refresh_documents.py`
  는 이 타입을 직접 참조하지 않는다.
- 확인: `uv run python -c "import app.services.documents.registered_resync"` 가
  통과할 것(가드가 잘못 걸리면 여기서 바로 드러난다).

### 2.4 문서 반영 완료 내역

코드 수정 전이라도 문구가 틀린 상태로 남으면 안 되므로 `02` 는 먼저 정정했다.

| 위치 | 변경 |
|---|---|
| 인셋 화살표 라벨 | `타입 전용 역참조` → `TYPE_CHECKING 역참조` |
| 인셋 우측 주석 | `typing 만 쓰는 leaf 모듈이라 / 런타임 결합이 없다` → `타입 검사 시점에만 존재한다 / 런타임 임포트 없음` |
| §2 figcaption | "타입 전용 임포트라" → "`TYPE_CHECKING` 으로 감싸 런타임에는 존재하지 않는 의존으로 좁히고" |

developer 수정이 들어오면 문서와 코드가 일치한다. **수정 전까지는 문서가 코드보다
반 발 앞서 있는 상태**이므로, developer 작업이 반려·보류되면 위 3개 문구를 되돌려야 한다.

보류를 판단하고 있다. 그 판단이 실 코퍼스 값에서도 유지되는지는 별건이고, 검토문서는
시점 기록이라 소급 수정 대상이 아니다. 다만 **다음에 검색 품질 우선순위를 다시 잡을 때는
doc/09가 아니라 doc/29 §13을 기준선으로 삼아야 한다** — lead 판단이 필요하면 별도로 올린다.
