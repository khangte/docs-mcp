# pdf/docx의 결정론적 개요-캐치올 — 게이트 전제 재판단

- 상태: **판단 only** — 코드 미수정.
- 일시: 2026-08-13
- 작성: architect
- 계기: developer 실측 — pdf/docx로 색인되는 문서는 '가끔'이 아니라 **구조적으로 100% section_count=1**(전체가 "개요" 캐치올). `markdown_parser`는 리터럴 `#` 줄만 헤딩으로 보는데 `pdf_parser`(pypdf)/`docx_parser`(python-docx)는 서식 없는 순수 텍스트만 뽑아 `#`가 나올 수 없음. Phase0 '0건'은 코퍼스에 실제 pdf/docx가 없었거나 짧았을 뿐, 쓰이는 순간 결정론적으로 해당.

## 0. 결론 먼저

developer 실측은 게이트 전제를 **실제로 흔든다** — 판정을 **수정**한다.

1. **pdf/docx는 투기 대상이 아니라 문서화·광고된 1급 색인 경로다**(README §C 직접 등록, §D Drive가 PDF/DOCX/XLSX/PPTX 자동 추출). → 발생은 "확률적"이 아니라 **"결정론적, 시간 문제".**
2. **단, developer의 '구조 분할이 전혀 안 됨' 프레이밍은 절반만 맞다** — **헤딩 구조는 없지만(section_count=1), 문단/페이지 `\n\n` 구조는 추출 텍스트에 살아있다.** pdf=`"\n\n".join(pages)`(pdf_parser:31), docx=`"\n\n".join(paragraphs)`(docx_parser:27). **doc/23의 문단(`\n\n`) 그리디 분할이 바로 이 경계를 탄다** → doc/23이 이 케이스의 적절한 해법이 **맞다**.
3. **판정 변경**: doc/23을 "실사례 트리거 대기(gate-B)"에서 **"지금 배선까지 진행(구현 착수)"로 상향**. 근거: 트리거가 결정론적으로 임박 + 배선 비용이 긴 섹션 없을 땐 사실상 0(조건부라 짧은 섹션은 1:1 유지) + 광고된 기능의 조용한 열화 창을 닫음. **doc/25(무조건 N:1 반려)와 무모순** — 조건부 분할이라 짧은 섹션은 여전히 1:1.

## 1. (질문1) pdf/docx가 운영 코퍼스에 쓰일 계획/가능성

**있다 — 결정적이다.** 근거:

| 근거 | 위치 |
|---|---|
| `register_document`에 `doc_type="pdf"/"docx"` base64 등록이 **문서화된 1급 경로** | README §(C) |
| Drive 소스가 **PDF/DOCX/XLSX/PPTX 바이너리를 텍스트 추출해 검색 대상화** | README §(D):274-277 |
| 전용 파서가 이미 존재·배선 | `pdf_parser`, `docx_parser`, `pptx_parser`, `xlsx_parser` |
| 라우터가 pdf/docx를 markdown_parser로 섹션화(헤딩 없음 확정) | `document_router.py:79-80` |

→ Phase0 '0건'은 **표본 아티팩트**(코퍼스에 실제 pdf/docx 부재/짧음)이지, "안 일어남"의 증거가 아니다. docs/13 교훈(작은 픽스처가 결론 왜곡)이 **이번엔 게이트를 여는 쪽으로** 작동한다.

## 2. (질문2) 트리거가 이미 충족된 것으로 봐야 하나

**정밀히**: 트리거는 "**현 코퍼스에 이미 충족**"이 아니라 "**첫 실 pdf/docx 사용 시 결정론적으로 충족**"이다. 구분이 중요하다.

- 지금 DB에 512 초과 실사례는 없다(Phase0 0건, 스크래치 제외).
- 그러나 pdf/docx는 헤딩이 **원리적으로** 없어 → 문서 전체가 1 섹션 → **본문이 1페이지(~약 512토큰) 넘는 순간 truncation 결정론적.** 실무 pdf/docx(다중 페이지 리포트)는 이를 쉽게 초과 → **비자명한 pdf/docx면 사실상 확정.**
- section_count=1은 **결정론적**, truncation은 **길이 조건부**(짧은 1페이지 pdf는 안전). 두 개를 섞지 않는다.

**결론**: "이미 터진 문제"는 아니지만 "확률이 아니라 시간 문제인, 광고된 기능의 예정된 결함"이다. 게이트의 목적(투기 회피, docs/15)에 비춰 — 이건 더는 투기가 아니다. **cheap 확증 1스텝으로 게이트를 실증 종료**하는 게 옳다: developer가 **실무급 다중 페이지 PDF 1건 등록 + Phase0 스크립트 재실행** → 결정론이라 반드시 초과가 뜬다. 이걸로 "구조 논증"이 "측정 사실"이 되어 docs/13·15를 유의미 지연 없이 만족.

## 3. (질문3) 근본 해법 — sub-chunking(doc/23) vs 추출단 구조 보강

두 후보는 **경쟁이 아니라 서로 다른 계층이며 상보적**이다.

| 후보 | 계층 | 효과 | 한계 |
|---|---|---|---|
| **doc/23 sub-chunking** | chunk 빌드(임베딩 예산 안전망) | 소스 무관, **truncation 원천 차단**. pdf/docx의 `\n\n`(페이지/문단) 경계를 그리디로 탐. 단일 문단이 예산 초과해도 문장→토큰 하드컷 폴백으로 **우아하게 저하** | parent(섹션) 경계 자체는 안 고침(여전히 1 섹션) |
| **추출단 구조 보강** | 파서(parent 품질 개선) | 진짜 헤딩/섹션을 만들어 parent 경계·반환 스코프 개선 | **docx만 유효**(python-docx `paragraph.style` = "Heading N" 감지 가능). **pdf는 불가**(pypdf 순수 텍스트에 서식 신호 없음 — 폰트크기 휴리스틱은 불안정) |

**판정: doc/23이 truncation의 근본 해법이 맞다.** 이유:
- truncation의 진짜 원인은 "임베딩 예산 초과"다. "헤딩 분할 없음"은 그 원인의 원인일 뿐. **예산 안전망(doc/23)만이 전 소스(특히 구조화 불가한 pdf)에서 truncation을 확실히 없앤다.**
- 추출단을 완벽히 해도 안전망은 여전히 필요: docx 헤딩 하나가 512를 넘을 수 있고, pdf는 애초에 신뢰할 구조가 없다. → 추출 보강은 **doc/23의 대체가 아니라 후속 보완**.
- developer의 '구조가 전혀 없다'는 프레이밍을 정정: **문단 구조는 텍스트에 있다**(`\n\n`). doc/23은 그 위에서 동작하므로 "구조가 없어 doc/23이 부적절"은 성립 안 함 — 오히려 doc/23이 정확히 그 경계를 쓴다.

**추출단 구조 보강은 별도 후속 트랙**(주로 docx heading-style 감지 → 더 나은 parent). parent 검색 배선(doc/24 C표 4행)과 묶어 판단할 사안이지, doc/23의 선행조건도 대체재도 아니다.

## 4. 판단 요약 (lead 결정 사항)

1. **doc/23을 gate-B(대기)에서 구현 착수로 상향 권고.** 조건부 분할이라 doc/25(무조건 N:1 반려)와 무모순 — 짧은 섹션 1:1 유지, 예산 초과 섹션만 N:1.
2. **cheap 확증 1스텝**(권고): developer가 실무급 다중페이지 PDF 1건 등록 + Phase0 재실행 → 결정론적 초과 확인으로 게이트 실증 종료(docs/13·15 준수). 결과 무관하게 구조 논증만으로도 착수 정당하나, 측정으로 못박는 게 이 프로젝트 규율에 부합.
3. **재색인 비용**: 현 코퍼스에 긴 섹션이 없다면 배선+재색인은 사실상 no-op(전부 예산 이하 → 1:1 유지). pdf/docx 유입 시부터 자동 분할. → **지금 배선 비용이 낮고 미래 결함 창을 닫음.**
4. **추출단 구조 보강(docx heading-style 등)은 별도 후속 트랙** — doc/23 이후, parent 검색 배선과 묶어 판단.
5. **스크래치 데이터 정리**: `scratch-heading-measure` project의 document 2건 정리 지시 필요.
