# 31. 배치 자동화 적용 대상 특정 및 설계 — 검색품질 평가 재측정 배치

- 작성: architect
- 요청: 사용자 "배치 자동화를 적절하게 적용해야돼. 어떻게 처리하면 좋을지 검토해줘." (대상 미지정)
- 선행 문서: `docs/architect-review/28-search-quality-eval-real-corpus-design.md`,
  `docs/architect-review/30-search-quality-eval-real-corpus-results.md` §12~14
- 대상 코드: `tests/fixtures/corpus_eval/run_corpus_eval.py`, `tests/fixtures/rrf_eval/`

---

## 1. 대상 특정 — 어느 "배치"인가

요청에 대상이 없어, 코드베이스에서 "배치"로 불릴 수 있는 반복 실행 단위를 전부 열거하고
자동화 이득이 실증된 것을 하나 고른다.

| 후보                     | 실체                                                          | 반복성                                                              | 판정               |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------------------------------- | ------------------ |
| (a) 검색품질 평가 재측정 | `tests/fixtures/corpus_eval/run_corpus_eval.py`               | doc/30 §8.1·§10.2·§11.4·§13에서 최소 4라운드 수동 실행, 결과 손전사 | **자동화 대상**    |
| (b) 협업문서 메타 동기화 | `refresh_index` MCP 도구 → `document_index_service.refresh()` | 클라이언트가 필요 시 호출                                           | 자동화 부적합(2절) |
| (c) 재임베딩             | `app/scripts/reembed.py`                                      | 임베딩 모델·차원 교체 시 1회성                                      | 대상 아님          |
| (d) 개발 하네스          | `harness/` (planner·generator·evaluator)                      | 개발 프로세스 문서, 실행 배치 아님                                  | 대상 아님          |

**판정: (a) 검색품질 평가 재측정 배치를 자동화 대상으로 특정한다.**

근거는 "반복이 실제로 일어났고, 그 반복이 실제로 사고를 냈다"는 점이다.

- 라운드마다 사람이 두 번 실행하고(콜드 / `--with-variants`), stdout 마크다운을 문서로 옮겼다.
- doc/30 §12.4가 지적한 "§8.1·§10.2가 변형 조건을 서로 다르게 섞어 **비교 축이 흐트러졌다**"는
  것은 절차 실수가 아니라 **조건 축이 실행 단위 밖에 있어서 생긴 구조적 결함**이다.
- §13.3의 신규 회귀(`get user information`) 1건은 사람이 표를 눈으로 대조해 발견했다.
  라운드 간 자동 비교가 없으므로 다음엔 놓쳐도 아무도 모른다.
- 다음 게이트인 **질의셋 확장(C5 우선, n=20 → 60~100)** 이 이 비용을 3~5배로 키운다.
  질의 100개 × 4개 arm이면 per-query 표가 400셀이다 — 손전사로 유지되지 않는다.

## 2. (b) refresh_index에 스케줄러를 붙이지 않는 이유 (명시적 반대 판정)

"배치 자동화"를 문서 재색인 쪽으로 읽을 여지가 있으므로 판정을 남긴다.

이 서버는 MCP stdio 서버다. README가 명시하듯 **클라이언트가 필요할 때마다 프로세스를 직접
실행**하며 상주 프로세스가 없다. 여기에 크론·APScheduler를 내장하면:

- MCP 클라이언트 세션 수만큼 스케줄러가 중복 기동해 같은 소스를 동시 갱신한다.
  중복 방지를 하려면 리더 선출이나 DB 어드바이저리 락이 필요하다 — 배치 하나 때문에
  분산 조율 문제를 새로 들인다.
- 클라이언트가 서버를 내리면 스케줄도 같이 죽는다. "주기 실행"이라는 계약을 지킬 수 없다.

**판정: 서버 프로세스 내부 스케줄링은 반려.** 협업문서 메타를 주기 갱신해야 하는 요구가
실제로 생기면, 서버 밖 상주 러너(호스트 cron이 `python -m app.scripts.<refresh>` 실행)로
분리하는 것이 옳은 형태다. 그 요구가 아직 제기된 적 없으므로 지금은 만들지 않는다(YAGNI).

## 3. 현행 (a) 배치의 수동 비용 — 무엇을 없앨 것인가

`run_corpus_eval.py`를 doc/30 §13 절차대로 돌리면 사람이 하는 일은 다음 5가지다.

1. **프로세스 2회 실행.** 조건 A(콜드) / B(변형)가 별개 실행이라 **temp DB 생성 + 20MB 스펙
   색인 + 전량 로컬 임베딩을 두 번 지불**한다. 정작 `--with-variants`는 질의 시점 옵션
   (`run_corpus_eval.py:134`)이라 색인과 무관하다 — 색인 절반이 순수 낭비다.
2. **조건 간 인덱스 동일성이 사람 절차에만 의존.** 두 실행 사이에 코드가 바뀌면 두 표는
   비교 불가지만 산출물에는 그 사실이 안 남는다(§12.4가 겪은 문제).
3. **stdout → 문서 손전사.**
4. **라운드 간 비교가 육안.** 신규 회귀 편입 여부를 사람이 표 대조로 찾는다.
5. **사전 점검이 수동.** §13이 "`queries.json`에 C2 4건·C7 2건 변형이 모두 존재함을 실행 전
   확인했다"고 적은 그 확인이 코드에 없다.

## 4. 자동화 범위 — 넣을 것과 넣지 않을 것

**넣는다: 실행 통합 · 결과 수집 · 라운드 간 비교 · 사전 점검.**

**넣지 않는다: CI 상시 실행, 스케줄러, 오케스트레이션 프레임워크, 결과 DB·대시보드.**

- CI를 지금 안 붙이는 근거: 실행 1회가 대형 스펙 색인 + CPU 임베딩이다. 스크립트 docstring이
  이미 "CI 상시 실행용이 아니라 수동 회귀 재실행 용도"로 못박았고, 이 저장소에는 워크플로가
  하나도 없다(러너 환경에 pgvector + sentence-transformers를 새로 세워야 한다).
  **선행 조건은 시간 측정이다**(Task 0). 1회 벽시계가 5분 이내로 나오면 그때 수동 트리거
  (`workflow_dispatch`) 또는 nightly 워크플로를 별건으로 재검토한다. 측정 없이 CI부터 세우는
  것은 근거 없는 인프라 지출이다.
- 결과 DB·대시보드: 라운드 수가 한 자릿수다. 파일로 충분하다.
- 질의 생성 자동화(LLM 배치): 별건이며 지금 우선순위 아님(7절).

## 5. 설계

### Task 0 — 기준선 측정 (선행, 코드 변경 없음)

현행 1회 실행의 벽시계 시간과 색인 소요를 측정해 기록한다(`time` 출력 그대로).
이후 Task 1의 효과(색인 1회화)와 CI 편입 가부 판단의 근거가 된다.

### Task 1 — 한 실행 = 한 색인 = 4개 arm

- `--with-variants` 불리언을 **조건 축**으로 승격한다: `--conditions cold|variants|both`
  (기본 `both`). 기존 `--with-variants`는 제거한다(호출처는 문서뿐이며 doc/30에 절차가
  기록돼 있으므로 하위호환 별칭 불필요).
- 색인은 실행 초입 1회. 이후 `strategy(2) × condition(2)` 루프로 4개 arm의 rank 벡터를 얻는다.
  전략 전환은 이미 `state.search_strategy` 재설정 + `build_services` 재호출로 저렴하며
  (`run_corpus_eval.py:187-189`) 재색인이 없다. 조건 전환은 `CandidateSearchOptions.query_variants`
  전달 여부뿐이다.
- arm 키는 `"{strategy}/{condition}"`(예: `rrf/variants`)로 통일하고 표·JSON·비교가 모두 이
  키를 쓴다.
- **이득**: 색인 비용 절반, 그리고 §12.4가 지적한 비교 축 붕괴의 **근본 수정** —
  네 arm이 같은 인덱스에서 나왔음이 실행 단위로 보장된다.

### Task 2 — 결과를 파일로 (전사 제거)

- `--out DIR`(기본 `output/eval/`). 산출: `output/eval/<UTC타임스탬프>-<git sha 7>/`
  아래 `results.json` + `results.md`.
- `results.json` 스키마(재현 메타 포함이 핵심):
  ```json
  {
    "run": {
      "ts": "...",
      "git_sha": "...",
      "corpus_sha256": { "stripe": "...", "github": "..." },
      "n": 20,
      "top_k": 10,
      "is_semantic": true,
      "embedding_model": "..."
    },
    "arms": [
      {
        "arm": "rrf/variants",
        "metrics": {
          "recall": { "1": 0.15, "3": 0.25, "5": 0.4, "10": 0.5 },
          "mrr": 0.248,
          "ndcg10": 0.308
        },
        "by_category": [
          { "category": "C5-decoy구분", "n": 3, "recall3": 0.0, "mrr": 0.15 }
        ]
      }
    ],
    "queries": [
      {
        "id": "q01",
        "query": "...",
        "category": "...",
        "accepted": [["GET", "/v1/..."]],
        "ranks": { "rrf/variants": 3, "fallback/cold": null }
      }
    ]
  }
  ```
  `corpus_sha256`은 이미 매니페스트 검증에서 읽는 값을 재사용한다(신규 계산 불필요).
- `results.md`는 현행 stdout 표를 그대로 파일로 쓴다. 문서에는 붙여넣기만 한다.
- `output/eval/`은 `.gitignore`에 추가한다(라운드 원자료는 리포에 쌓지 않는다).
  문서에 남길 것은 `results.md`에서 발췌한 표와, 5.3의 승격된 baseline뿐이다.

### Task 3 — 베이스라인 비교 (재판정 자동화)

- `--baseline PATH`(기본 `tests/fixtures/corpus_eval/baseline.json`, **커밋 대상**).
  파일이 없으면 비교를 건너뛰고 안내만 출력한다.
- 출력 3종:
  1. arm별 지표 델타 표(현재 − baseline).
  2. 질의 단위 순위 변화(개선/악화만, 무변화 생략).
  3. **신규 회귀 목록** — baseline에 없던 "fallback 대비 rrf 열위" 케이스. §13.3의 발견을
     사람 눈이 아니라 코드가 한다. 해소된 회귀도 같이 낸다.
- **자동 PASS/FAIL 판정은 넣지 않는다.** n=20의 표준오차가 ±11%p대(§12.5)라 임계 판정은
  통계적 근거 없는 신뢰를 만든다. 대신 델타 표 하단에 현재 n 기준 참고 오차 한 줄을 고정
  출력하고, 해석은 architect가 한다.
- `--promote-baseline`: 방금 실행 결과를 baseline으로 승격. 라운드 종결 시 architect 승인
  후 developer가 실행한다.
- baseline의 n이 현재 n과 다르면(질의셋 확장 직후) **절대 지표 비교는 무의미**하므로
  경고를 출력하고 카테고리별 비율만 비교한다.

### Task 4 — 진입점 하나

- `scripts/run_eval.sh`: postgres 기동 확인 → 본 실행(`--conditions both --baseline ...`) →
  산출 경로 출력. 라운드 실행이 **명령 한 줄**이 된다.
- 사전 점검(라벨 정합성은 기존 `_load_and_validate_queries`, 변형 존재 여부는 신규)은
  **스크립트가 아니라 파이썬 실행 초입**에 둔다. 셸에 검증 로직을 복제하지 않는다.
  - 변형 점검 규칙: `--conditions`에 `variants`가 포함됐는데 변형 보유 질의가 0건이면 에러,
    일부면 "변형 보유 6/20"처럼 건수를 출력하고 진행(현재 20질의 중 6건 보유).

### 완료 기준

- `scripts/run_eval.sh` 한 번으로 4개 arm 지표표 + 카테고리 분해 + 회귀 목록 + baseline 델타가
  파일로 남는다.
- 색인은 실행당 1회다(Task 0 대비 시간 단축이 실측으로 확인된다).
- 단위 테스트: baseline 델타 계산과 신규 회귀 판별을 **rank 딕셔너리만 입력받는 순수 함수**로
  분리해 `tests/unit/`에서 DB 없이 검증한다(`tests/unit/test_eval_metrics.py`와 같은 결).
  실행 스크립트 본체는 기존대로 pytest 수집 대상이 아니다.

## 7. 질의셋 확장(C5 우선)과의 순서

**자동화를 먼저 넣고 확장한다.** n=60~100 라운드를 수동 절차로 돌리면 per-query 표가
수백 행이 되어 기록 자체가 무너진다(3절 3·4번 비용이 선형으로 커진다). 순서는:

1. Task 0~4 반영.
2. 현행 n=20 결과를 baseline으로 승격(확장 전 마지막 비교 기준점 확보).
3. 질의셋 확장(C5 우선) 후 재측정 — 이때 baseline의 n 불일치 경고가 뜨며 카테고리 비율
   비교로 전환된다.

질의 **생성** 자동화(LLM 배치 생성)는 이 검토의 대상이 아니다. C5 확장의 병목은 생성이
아니라 **라벨 정확도에 대한 사람 검수**이고(`eval-set-expansion-plan.md` 1.3이 라벨을 좁게
유지하라고 규정한 이유), 생성을 자동화해도 그 병목은 안 풀린다.

## 8. 요약

- 자동화 대상은 **검색품질 평가 재측정 배치** 하나다. 문서 재색인 쪽 스케줄링은 MCP stdio
  구조상 반려한다.
- 핵심은 "돌리는 걸 자동화"가 아니라 **조건 축을 실행 안으로 넣어 비교 가능성을 구조로
  보장하고, 라운드 간 비교를 코드가 하게 만드는 것**이다. 실행 횟수를 줄이는 것은 그 부산물이다.
- CI·스케줄러는 지금 넣지 않는다. Task 0의 실측 시간이 그 판단의 입력이다.
