# 53. 비즈니스 메타데이터 1단계 게이트 판정

- 판정일: 2026-08-25
- 대상: [52. 비즈니스 메타데이터 설계안 검토](52_business_metadata_design_verdict.md) 의 측정 계획 1단계(description 청크 제외 단독 A/B) 결과
- 측정 수행: developer (DB 정상 기동 확인, `chunk_builder.py` 실험 후 원복 — 워킹트리 clean)
- **판정: 반려. 2단계(스키마 마이그레이션) 착수 보류. 1b 실험을 먼저 수행한다.**
- 이 문서는 52 §측정 계획의 1단계 게이트 조건과 2단계 진입 조건을 대체한다.

## 1. 측정 결과 정리

| 조건                    | 0단계(기준선) R@3 / MRR | 1단계(description 제외) R@3 / MRR |
| ----------------------- | ----------------------- | --------------------------------- |
| variants off · fallback | 35% / .307              | 30% / .214                        |
| variants off · rrf      | 30% / .303              | 30% / .202                        |
| variants on · fallback  | 35% / .299              | 25% / .198                        |
| variants on · rrf       | 35% / .367              | 25% / .219                        |

카테고리별:

| 카테고리                      | 0단계                                   | 1단계                                                |
| ----------------------------- | --------------------------------------- | ---------------------------------------------------- |
| C5(decoy 구분, n=3)           | fallback 100% / rrf 67% (variants 무관) | 4개 조건 전부 0%                                     |
| C7(대형 엔드포인트 세부, n=3) | 4개 조건 전부 0%                        | variants off 67%(양 전략) / variants on 33%(양 전략) |

건별 뒤집힘은 developer 보고 그대로다. 요약하면 C5 3건 전부 하락(q13 rank1→rank7/5, q14 rank3→미검출,
q15 rank3/2→미검출/rank5), C7은 q19·q20 상승, q18은 4개 조건 전부 미검출 유지.

## 2. 판정 근거

### (a) 집계는 혼재가 아니다 — 4개 조건 전부 악화됐다

보고는 "혼재 결과"로 요약했으나, 집계 수준에서는 혼재가 아니다. **recall@3은 4개 조건 중 3개에서
떨어지고 1개에서 동률이며, MRR은 4개 조건 전부에서 떨어진다.** 하락폭도 작지 않다 —
최고 조건(variants on · rrf)에서 .367 → .219 로 상대 40% 하락이다.

recall@3이 유지되는데 MRR이 크게 떨어지는 패턴은 C5 3건만의 문제가 아니라 **정답 순위가 전반적으로
밀렸다**는 뜻이다. 20건 전체에서 일어난 일이다.

이는 52 §(a) 조건 2에서 경고한 경로와 일치한다 — description 제거는 임베딩 입력에서만이 아니라
`chunk.text_tsv` 에서도 토큰을 지운다. 임베딩은 1406토큰 절단 문제가 있어 제거가 이득일 수 있지만
렉시컬 인덱스에는 절단이 없었으므로 순수 손실이다.

### (b) 표본 크기 우려는 방향이 반대다 — 의심해야 할 쪽은 C7의 상승이다

C5 n=3이라 노이즈 아니냐는 질문에 대한 답: **C5 하락은 노이즈가 아니다.**

- 3건이 전부, 4개 조건 전부(=12관측)에서 같은 방향으로 움직였다.
- q13은 rank 1 → rank 7 이다. 경계에서 한 칸 밀린 것이 아니라 오답 6개가 정답을 앞질렀다.
- n=20 집계 MRR이 4개 조건 전부에서 하락한 것이 독립적으로 이를 뒷받침한다.

반대로 **C7의 상승이 뒷받침이 약하다.**

- 집계 지표가 같이 오르지 않았다(전부 하락). C7 3건의 이득이 나머지 17건의 손실에 묻혔다.
- q19가 조건에 따라 rank3 ↔ 미검출로 요동친다(variants off 양 전략 rank3, variants on은 fallback
  미검출 / rrf rank10). 조건 간 이 정도 편차는 안정된 신호의 모습이 아니다.
- q18은 개선이 없다. 실질 상승은 q20 단독(rank 4~5 → rank 3)에 q19의 불안정한 이득이 붙은 것이다.

따라서 "C7은 살고 C5는 죽었다"가 아니라 **"C5는 확실히 죽었고, C7은 아마도 조금 좋아졌다"** 로
읽어야 한다.

### (c) 52의 사전 가설은 절반만 기각됐다

가설: "C7 정답 정보가 상당 부분 body 필드명에 있으므로 `Body:` 줄이 C7을 살릴 것이다."

q18(currency)에서 기각됐다 — 4개 조건 전부 미검출이다. `Body:` 줄이 있어도 stripe `/v1/charges` 는
찾지 못한다. 이 가설로는 C7 개선을 설명할 수 없다.

**더 잘 맞는 설명이 있다: description 제거가 대형 엔드포인트에서 희석·절단을 걷어냈다.**
52 §미해결에 적어 둔 stripe description HTML 태그 99.2% 문제가 여기에 걸린다. 대형 엔드포인트 청크는
`token_limit=480`(`app/services/indexer/chunk_builder.py`)에 이미 걸려 잘리고 있고, 그 자리를 HTML
마크업이 섞인 장문 산문이 차지하고 있었다. description을 빼자 잘려 나가던 구조 필드가 살아난 것이다.

이 설명이 맞다면 C7의 처방은 **description 삭제가 아니라 description 정리(HTML strip + 길이 절단)** 다.
그리고 그 처방은 C5를 죽이지 않는다 — github description은 짧고 HTML이 거의 없다.

### (d) 결론: "description 전면 대체" 전제는 죽었다

52는 C7 붕괴를 킬 조건으로 지정했고 C7은 붕괴하지 않았다. 그러나 같은 문서에서
"집계값만으로 승인하지 않는다, 건별로 본다"를 조건으로 걸었다. 건별로 보면 실패가 C7이 아니라 C5에서
났을 뿐, 전제가 무너진 것은 같다. **게이트 조건이 킬 지점을 한 카테고리로 좁게 지정한 것이 설계 오류였다.**
판정은 문구가 아니라 측정에 따른다 — 반려한다.

확정 사항: **business metadata는 description의 대체(replacement)가 아니라 추가(addition)로 들어간다.**
청크 텍스트에서 description을 완전히 제거하는 갈래는 폐기한다.

## 3. 2단계를 지금 승인하지 않는 이유

"어차피 metadata를 추가로 넣을 거면 스키마는 필요하니 2단계는 진행해도 되지 않나"에 대한 답:
**아니다. 청크 포맷을 먼저 확정해야 한다.**

- 대형 엔드포인트 청크는 이미 480토큰에서 잘린다. 52 §(3)이 확정한 배치는 `Keywords:` / `Phrases:` 를
  header 직후에 넣는다. **절단이 걸린 청크에 앞줄을 추가하면 꼬리의 `Body:` 필드명이 밀려 나간다.**
  그런데 이번 측정에서 C7을 살린 것이 바로 그 `Body:` 줄일 가능성이 크다((c)). metadata 추가가
  C7 이득을 스스로 깎아먹는 구조다. 이 상호작용을 모른 채 스키마·CLI·LLM 파이프라인을 다 만들면
  가장 비싼 작업을 끝낸 뒤에 포맷을 다시 뒤집게 된다.
- 이번 측정이 보여준 실질 이득(C7 0% → 67%)은 **스키마 0줄, LLM 호출 0회, `chunk_builder.py` 단독
  수정으로 나왔다.** 같은 자리에서 C5를 되살릴 수 있는지가 아직 미측정이다. 그게 되면 metadata
  파이프라인 없이 목표의 상당 부분이 끝난다. 확인하지 않고 인프라부터 만드는 것은 YAGNI 위반이다.

## 4. 지시: 1b 실험 (developer)

`chunk_builder.py` 단독 수정. 스키마·CLI·파서 변경 없음. 실험 후 원복은 1단계와 동일하게 한다.

description을 **제거하지 않고 정리**한다. 두 효과를 섞지 않도록 arm을 나눈다.

- **arm A — HTML strip only**: description에서 HTML 태그만 제거하고 길이는 그대로 둔다.
- **arm B — HTML strip + 절단**: A에 더해 description을 앞 300자에서 자른다(문장 경계 무시, 단순 절단).

각 arm마다 재색인 후 기존과 동일하게 4조건(`--strategy both` × `--with-variants` on/off) 측정.
카테고리별 recall@3 / MRR 과 **C5·C7 6건의 건별 rank** 를 함께 보고한다. 집계만으로는 판정하지 않는다.

판정 기준:

| 결과                                                                                      | 결론                                               | 다음                                                                                               |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| C5가 기준선(fallback 100% / rrf 67%) 회복 **그리고** C7 > 0% **그리고** 집계 MRR ≥ 기준선 | description 정리만으로 목표 달성                   | 2단계 승인. 단 metadata 범위를 C2/C7 한정으로 축소 재검토                                          |
| C5 회복, C7은 0% 복귀                                                                     | description은 유지 확정, C7은 metadata로 별도 공략 | 2단계 승인 (포맷은 아래 조건)                                                                      |
| C5 미회복                                                                                 | 절단·strip 자체가 유해                             | arm A/B 중 손실이 적은 쪽으로 되돌리고 description 원문 유지 확정. 2단계는 승인하되 포맷 조건 강화 |

어느 경우에도 **description 완전 제거로 돌아가지 않는다.**

### 2단계로 넘어갈 때 함께 적용되는 포맷 조건 (52 §(3) 수정)

1b 결과와 무관하게 확정한다.

- `Keywords:` / `Phrases:` 를 header 직후에 두는 52 §(3)의 배치는 **보류한다.** 절단이 걸리는 대형
  엔드포인트에서 `Body:` 를 밀어내기 때문이다. 배치는 1b로 확정된 청크 구성 위에서 A/B로 다시 정한다.
- BusinessDesc는 description을 **대체하지 않고 병기**한다. 병기가 절단 예산을 넘기면 그때 무엇을
  줄일지 측정으로 정한다.

## 5. 하네스에 대한 정정

52 §측정 계획은 "하네스는 수정 불필요"라고 적었으나, 같은 문서 §(a) 조건 2가 요구한
**벡터 갈래 / 키워드 갈래 분리 측정은 현 하네스로 불가능하다.**
`run_corpus_eval.py --strategy` 의 선택지는 `rrf` / `fallback` / `both` 뿐이고, 이는 융합 전략이지
검색 갈래가 아니다. developer가 보고한 fallback·rrf 두 축은 지시를 잘못 따른 것이 아니라
하네스로 가능한 최대치다. 조건 2는 이번 측정에서 충족되지 않았다.

1b에서도 갈래 분리는 요구하지 않는다. 1b의 판정은 C5 회복 여부로 갈리고, 갈래 분리는 원인을 설명할 뿐
결론을 바꾸지 않는다. 1b 결과가 다시 애매하게 나올 때 그때 하네스에 갈래별 모드를 추가한다.
