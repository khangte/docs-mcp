# 20. OpenAPI 스펙을 색인 소스로 삼는 접근의 타당성 재검토 (스펙 vs 코드)

> 별개 트랙 분석 리포트. 코드 변경 없음. 근거: `README.md`,
> `docs/archive/plan.md`, `docs/adr/0001`,
> `docs/exec_plans/docs_mcp_expansion/SPEC.md`, 파이프라인 코드.

사용자 지적: OpenAPI/Swagger 스펙은 실제 API 구현(코드)과 별도로 관리·수정되는
문서인데 진짜 구현은 코드에 있다 → 스펙 문서를 색인 소스로 삼는 접근 자체가
맞느냐.

**결론 요약**: 이 프로젝트에선 스펙 기반이 맞다. 전제가 어긋난 지점이 있다 —
docs-mcp 는 "내 코드베이스를 이해하는 도구"가 아니라 **대상 코드를 대개 보유하지
않는(서드파티·이종 포맷) 문서 검색 MCP 서버**다. drift 는 실재하지만 이
시스템의 책임 밖(경계)이며, 그 완화책도 "코드 파싱"이 아니라 **자동생성 스펙
엔드포인트 등록**으로, 지금 구조가 이미 수용한다.

---

## 1. 스펙을 소스로 삼는 이유 (근거 기반)

### 1-1. 이 시스템은 "문서 검색 서버"이지 "코드 분석 도구"가 아니다

- `README.md`: "OpenAPI(Swagger)·**Markdown·CSV** 문서와 **Google Drive/Notion**
  협업 문서를 수집·색인하고 하이브리드 검색." → OpenAPI 는 **5개 문서 포맷 중
  하나**. 시스템의 본질은 이종 문서 RAG 이지 API 코드 해석이 아니다.
- `SPEC.md` 공통 원칙: "**Generation 은 항상 호출 LLM 담당, 서버는 찾아주는
  역할까지**." 즉 문서를 뒤져 근거를 대는 검색 계층이다.
- 코드 파싱은 이 스코프의 **대부분(MD/CSV/Drive/Notion)을 커버하지 못한다** —
  이들엔 "코드"가 없다.

### 1-2. 대상 API 코드를 대개 **보유하지 않는다**

- `plan.md §2`: "탐색 대상이 되는 OpenAPI 명세는 사전에 MCP 서버와 연결되어
  있어야 하며 … 클라이언트는 Swagger 원본에 직접 접근하지 않고 서버가 제공하는
  조회 기능으로 API 정보에 접근." → 사용자(개발자)가 붙이는 건 **명세 문서(URL/
  텍스트)**다. 대상이 서드파티 API 면 **구현 코드는 애초에 접근 불가**하고,
  기계가독 계약물은 OpenAPI 스펙뿐이다. 스펙이 유일하게 파싱 가능한 진실원.
- `register_document` 는 URL 또는 raw text 로 등록(`api_document.source_url`
  UNIQUE) — 원격/외부 스펙 수집 전제. 코드 저장소를 가리키는 개념이 없다.

### 1-3. "저장형(사전 색인)"은 의도된 설계 결정

- `ADR-0001`: "OpenAPI 를 실시간 프록시하지 않고 사전 수집·정규화해 로컬
  DB 에 저장·색인." 근거: 대용량 Swagger JSON 실시간 로드는 LLM 컨텍스트
  낭비·속도 저하. 스펙을 정규화해 endpoint/param/schema 단위로 쪼개 필요한
  것만 골라주는 게 목적. → 소스가 "스펙 문서"인 것은 이 목적의 자연스러운 귀결.

**정리**: 스펙을 쓰는 이유는 (a) 시스템이 범용 문서 검색기라 코드 개념이
없고, (b) 대상 코드는 대개 없으며 스펙이 유일한 기계가독 계약이고, (c) 사전
정규화·색인으로 LLM 에 선별 제공하는 게 설계 목표이기 때문.

---

## 2. 스펙↔코드 drift 를 지금 시스템이 어떻게 다루나 — **다루지 않는다(의도된 경계)**

- 현 sync 는 **저장된 스펙 vs 그 스펙의 출처(URL/텍스트)** 를 `content_hash`
  비교로 맞춘다(`refresh_index`, `sync_service`). 최신성 기준은 **스펙 원본**이지
  코드가 아니다.
- 시스템에 **코드를 관측하는 경로가 전무**하다(코드 저장소·정적분석·런타임
  관측 없음). 따라서 "스펙은 이런데 코드는 다르게 동작"을 **판별할 수단이 없다.**
- 이는 결함이 아니라 **경계**다: docs-mcp 는 문서 검색 계층이고, 스펙을 **권위
  있는 계약물로 간주**한다. 스펙이 코드와 어긋나 있으면 그건 **문서 자체의
  품질 문제**(garbage-in)이며, 어떤 문서 검색기도 원문이 틀리면 틀린 걸
  찾아준다 — MD/CSV/Notion 도 동일. 문서 진위 판정은 이 시스템의 책임이 아니다.
- `SPEC.md` 도 이를 명시적으로 전제: OpenAPI 는 "정형 스펙, URL 고정, **변경
  드묾**" 으로 분류하고 사전 색인 전략을 배정 — drift 를 능동 추적할 대상이
  아니라 안정적 계약물로 취급.

**요지**: drift 리스크는 실재하나, 현 시스템은 이를 **다루지 않으며 다루는 게
스코프도 아니다.** 스펙을 진실원으로 신뢰하는 게 전제다.

## 3. 코드를 소스로 삼는 대안 평가 — 이 프로젝트엔 **부적합**

| 대안 | 이 프로젝트에 맞나 | 근거 |
|---|---|---|
| **FastAPI 등 자동생성 스펙만 신뢰** | 부분적으로 옳으나 별도 기능 불필요 | 자동생성 스펙은 코드에서 나오므로 drift 없음 — 그러나 그건 결국 **`/openapi.json` URL 하나**다. 현 시스템은 그 URL 을 그냥 등록하면 됨. 새 코드가 필요 없음(§3-1). |
| **코드 정적분석으로 엔드포인트 추출** | 부적합 | (a) 대상 코드 미보유가 다수(서드파티). (b) 언어·프레임워크마다 추출기가 달라 **포맷 무관성**(범용 문서 검색이라는 핵심 가치)을 깨뜨림. (c) MD/CSV/Drive/Notion 은 커버 불가 — 시스템 스코프 대부분과 무관. (d) 하드코딩 라우트·동적 등록·미들웨어 인증 등 정적분석 사각지대. |

### 3-1. 사용자 우려의 진짜 해법은 "코드 파싱"이 아니라 "자동생성 스펙 등록"

"코드가 진실"인 상황(내 1st-party FastAPI/Spring 서비스)에서 drift 를 없애는
정석은:

- 손으로 유지하는 스펙 파일 대신 **프레임워크가 코드에서 자동생성하는 스펙
  엔드포인트**(FastAPI `/openapi.json`, springdoc `/v3/api-docs` 등)를 등록한다.
- 그 엔드포인트는 **코드에서 파생**되므로 스펙↔코드 drift 가 원천 소거된다.
- 그리고 이건 **현 시스템이 이미 지원**한다 — URL 등록 + `refresh_index`
  해시 sync 로 코드 배포 후 재색인까지 커버. **추가 구현 0.**

즉 사용자가 지목한 "스펙이 손으로 관리돼 코드와 어긋난다"는 리스크는,
시스템 아키텍처를 바꿔서가 아니라 **운영 관행(자동생성 엔드포인트를 소스로
등록)** 으로 해소된다. 코드 정적분석기를 내장하는 건 과설계이며(§17~18 과 같은
YAGNI 위반), 범용성·다포맷이라는 제품 정체성과도 상충한다.

## 4. 권고

1. **스펙 기반 접근 유지.** 코드 정적분석/코드 소스화는 도입하지 않는다 —
   제품 정체성(다포맷 문서 검색)·대상 코드 미보유·범용성 훼손 이유로 부적합.
2. **drift 는 시스템 밖 경계로 명문화.** docs-mcp 는 스펙을 권위 계약물로
   신뢰하고, 스펙↔코드 정합은 문서 소유자 책임임을 ADR 한 장으로 못박아
   같은 질문 재발을 막는다(선택).
3. **운영 가이드 한 줄 추가(선택, 문서만).** "1st-party API 는 손유지 스펙
   대신 프레임워크 자동생성 스펙 엔드포인트(`/openapi.json` 등)를 등록하라 —
   drift 원천 차단, 추가 기능 불필요." README/사용 가이드에 반영하면 사용자
   우려를 코드 변경 없이 실질 해소.

**최종 판정**: 스펙 문서 기반 접근은 이 프로젝트에서 여전히 옳다. 사용자가 든
drift 리스크는 타당하나, 해법은 아키텍처 변경(코드 파싱)이 아니라 자동생성
스펙 등록이라는 운영 관행이며, 현 구조가 이미 이를 수용한다.
