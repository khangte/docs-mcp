## 0. 결론 먼저

1. **lead의 결론은 맞다 — 키워드 arm 제거·전량 벡터화·Qdrant 전환 모두 비권장.** 다만 근거 하나는 "키워드 arm 제거" 전제 아래에서 **약해지므로 교체**해야 한다(1-3절).
2. **키워드 arm 제거는 순손실**이다. 벡터 arm이 약한 지점(정확 토큰 매칭)을 메우려 RRF 하이브리드를 도입한 것이고(docs/07), 키워드 arm에는 P1이 튜닝한 한글·혼합스크립트·경로분해 FTS 자산이 실려 있다(docs/09 P1). 제거하면 이 자산을 버린다.
3. **전량 벡터화는 최약점을 못 고친다.** 실측상 유일한 recall 약점인 교차언어(Recall@3 50%)는 **벡터 arm 자신의 약점**이다(docs/09 P1). 벡터 비중을 100%로 올려도 그 갭은 벡터가 만든 갭이라 안 닫힌다 — 오히려 키워드 arm이 잡던 일부를 잃어 **악화 가능**.
4. **Qdrant는 docs/06에서 두 번(초판·§7 전제완화) 판정 완료** — 스케일 동인 부재로 lateral move. "키워드 arm 제거" 전제는 초판의 결정 근거(크로스스토어 병합)를 약화시키지만, 결론은 불변(4절).
5. **잔여 RAG 레버 중 신규로 볼 만한 것은 단 하나 — 임베딩 모델 교체(교차언어 recall 직격).** docs/11 §5가 "인프라 판단"이라며 스코프 밖으로 뺀 항목이라 **retrieval 레버로는 미판정**. docs/12-B(문맥 청킹)가 같은 축1을 겨눴다 종결됐으므로, 축1의 남은 미탐색 레버는 이것이다(5절). 나머지(HNSW 파라미터·iterative_scan·멀티벡터 등)는 이미 판정됐거나 스케일 대기(6절).

## 1. "키워드 arm 제거 + 전량 벡터화" 검증

### 1-1. lead 근거 ①(FTS = 정확 토큰 매칭 담당, 벡터 약함) — ✅ 타당

- RRF 하이브리드의 **도입 목적 자체**가 벡터의 이 약점 보완이다(docs/07). path 리터럴(`/orders/{orderId}`), 파라미터명(`orderId`), 에러코드 같은 **정확 토큰**은 의미유사도가 아니라 어휘 일치로 잡아야 하고, 이건 FTS `ts_rank`의 영역이다.
- 키워드 arm은 단순 FTS가 아니라 **P1이 정밀 튜닝한 자산**이다 — 한글·혼합스크립트 토큰화(`GET요청`→`get`,`요청`), 경로 분해(`/orders/{orderId}`→`orders`,`orderid`)가 `TEXT_TSV_EXPRESSION` 정규식에 배선돼 있다(docs/06 §7-1, docs/09 P1). 제거 = 이 배포·튜닝 완료 자산 폐기.
- **실측 근거**: docs/09 P1 확장셋(84질의)에서 RRF는 fallback 대비 **전 지표 상회**(Recall@1 +9pt, MRR +0.084). 특히 "흔한 토큰 오탐 범람" 카테고리 MRR 0.552→0.812. 두 arm 융합이 단일 arm보다 낫다는 것이 측정돼 있다.

### 1-2. lead 근거 ②(다국어 임베딩도 교차언어 Recall@3 ≈ 50%, 100%로 올려도 갭 잔존) — ✅ 타당, 더 강하게

- 교차언어는 **벡터 arm 고유의 약점**이다(임베딩 기반). docs/09 P1: 교차언어 카테고리는 fallback·rrf **둘 다** 낮음(Recall@3 50%, MRR 0.3~0.5) — 전 카테고리 중 최약.
- 따라서 "벡터 비중 100%"는 논리적으로 **최약점을 만든 바로 그 arm의 비중을 키우는 것**이라 갭이 닫힐 수 없다. docs/09 P3가 명시: 교차언어의 절반은 정답이 top-3에조차 없는 **retrieval(recall) 문제**지 재배치 문제가 아니다.
- 오히려 키워드 arm(P1 한글 토큰화 + docs/12-A로 배선된 `query_variants` FTS 보강)이 교차언어를 **일부** 잡던 경로를 잃어 **악화 가능**. 전량 벡터화는 갭을 못 줄이고 잡던 것만 버린다.

### 1-3. 판정

**전량 벡터화 = 비권장(순손실).** 근거: (a) RRF가 단일 arm보다 전 지표 우세(실측), (b) 최약점(교차언어)은 벡터 자신의 약점이라 벡터 비중↑로 안 풀림, (c) 폐기 대상이 P1 튜닝 완료 FTS 자산. 이득 측 ≈ 0, 비용 측 = 측정된 이점 폐기.

## 2. "Qdrant 전환" 검증 — docs/06 참조 + "키워드 arm 제거" 전제의 영향

### 2-1. docs/06은 이미 두 번 판정했다

- **초판(§1~6)**: pgvector 유지. 결정 근거 = 단일 행(api_chunk) 분리 시 이중쓰기·크로스스토어 병합·스케일 부적합.
- **§7 전제완화 재검토**: 사용자가 "로직을 Qdrant에 맞춰 전면 재구성해도 된다"를 열자, 초판의 "크로스스토어 병합" 근거는 **약해짐을 정직하게 인정**하되(Qdrant 네이티브 하이브리드 B가 그 문제를 실제로 해소), 결론은 유지 — 이유는 ①네이티브 하이브리드는 pgvector도 마이그레이션 0으로 이미 제공, ②키워드 자산 격차, ③스케일 동인 부재, ④비용 즉시성 대 이득 잠재성. **사용자 최종 승인으로 pgvector 확정.**

### 2-2. "키워드 arm 제거" 전제가 Qdrant 판단을 바꾸는가 — 부분적으로, 결론은 불변

이번 질문은 docs/06 §7과 다른 새 전제를 하나 더 얹는다: **키워드 arm 자체를 없앤다.** 이 경우:

- **lead 근거 ③("pgvector가 관계형 메타와 같은 DB에 있어 단일 SQL 필터를 얻는다")은 약해진다.** 키워드 FTS가 사라지면 docs/06 초판의 결정타였던 "FTS와 벡터를 한 테이블에 둔 하이브리드 단일 SQL"이라는 이점 자체가 소멸하기 때문이다. 즉 **이 근거는 "키워드 arm 제거" 전제 아래에선 인용하면 안 된다** — 교체 필요.
- **그러나 Qdrant 비권장 결론은 유지된다**, 더 단순한 이유로:
  1. **스케일 동인 부재(불변·결정타)**: 로컬·단일 사용자·수천~수만 벡터. Qdrant의 차별 기능(샤딩·양자화·고급 HNSW·payload 필터)은 이 규모에서 전부 사표(docs/06 §1). 키워드 arm 유무와 무관.
  2. **관계형 메타는 여전히 Postgres에 남는다**: `project` 필터·태그·`get_endpoint_details`용 엔드포인트/문서 메타·원문은 관계형 SoR로 남아야 한다. 벡터만 Qdrant로 떼면 `document_id`/`project`/`ref_id`를 **payload로 복제**해야 하고(관계형 조인 → payload 필터 다운그레이드), 벡터 인덱스 갱신에 **이중쓰기·재조정 배치**가 붙는다(docs/06 §2). 키워드 arm이 없어도 이 축은 그대로다.
  3. **전면 재색인 + 컨테이너·백업 이원화·기동 의존**(docs/06 §4·§7-3) 즉시 발생, 이득은 스케일 없어 미발현.

### 2-3. 판정

**Qdrant 전환 = 비권장(불변).** 단 lead가 대사용자 답변에 쓴 근거 "단일 SQL 하이브리드 필터 상실"은 이번 "키워드 arm 제거" 전제와 **논리적으로 충돌**(그 전제가 하이브리드를 없앤다)하므로, 대신 **①스케일 동인 부재 ②관계형 메타 잔존에 따른 payload 복제·이중쓰기 ③전면 재색인 비용**으로 교체해 설명해야 한다.

## 3. 저비용 대안은 이미 있다

lead의 "안 함, `query_variants`가 이미 저비용 레버로 존재" — ✅ 정확. docs/12-A로 `query_variants`가 엔드포인트 키워드 arm FTS 후보 필터에 배선 완료(커밋 `c91cedb`). 동의어·한글↔영문 교차언어를 **클라가 명시적으로** 보강하는 재색인 0·신규 의존성 0 경로가 이미 가동 중이다. 전량 벡터화·Qdrant라는 대공사 없이 교차언어를 건드리는 현존 레버.

## 4. 잔여 RAG 레버 — 이미 판정된 것 vs 신규

docs/12 A/B/C 외에, "pgvector 내 벡터 arm 개선"으로 볼 수 있는 항목을 전부 훑어 판정 상태를 정리한다.

| 레버 | 상태 | 근거 문서 |
|---|---|---|
| HNSW `ef_search` GUC 상향 | **완료** (`SET LOCAL ef_search=max(100,top_k)`, 커밋 `aae5728`) | docs/09 P5 |
| RRF `K`/후보폭 `N` 스윕 | **완료·null result** (K=60 유지) | docs/09 P4 |
| 필드 가중 tsvector(setweight) | **보류** (한계이득 작음+재색인 규모, 실측 트리거) — 키워드 arm | docs/09 P2 |
| Cross-encoder 리랭킹 | **보류(HOLD)** = docs/12-C | docs/09 P3, docs/12 |
| 계층/문맥 청킹 | **실험 후 종결** (효과 없음, 픽스처 아티팩트) = docs/12-B | docs/13 |
| `query_variants` 키워드 arm 배선 | **구현 완료** = docs/12-A | docs/12, 커밋 `c91cedb` |
| LLM 질의확장(서버측) | **원칙 배제** | docs/09, docs/11 §5 |
| 정적 동의어/약어 사전 | **비권장(ROI)** | docs/09 |
| HNSW `iterative_scan`(over-filtering) | **인지·스케일 대기** | docs/09 P5, docs/11 S2 |
| 벡터 스코프 IN→JOIN(S2) | **구조 개선 대기**(성능, recall 무관) | docs/11 S2 |
| **임베딩 모델 교체(교차언어 recall 직격)** | **미판정(신규)** — docs/11 §5가 retrieval 레버가 아닌 "인프라 판단"으로 스코프 밖 처리 | 5절 |

**신규로 볼 만한 유일한 항목 = 임베딩 모델 교체.** 나머지는 전부 이미 판정됐거나 성능(recall 무관)/스케일 대기 건이다.

## 5. 신규 레버 — 임베딩 모델 교체 (교차언어 recall 직격, 방향 제안 only)

### 5-1. 왜 이것만 신규이고 볼 만한가

- **축1(retrieval recall) 직격**: docs/12는 "깊이"의 진짜 상방을 축1(recall)·축2(클라 순회)로 나눴고, 실측상 축1의 유일한 약점은 교차언어(Recall@3 50%). 축1을 겨눈 미탐색 레버로 docs/12-B(계층/문맥 청킹)를 지목했으나 **docs/13에서 효과 없음으로 종결**됐다. 그러면 축1에 남은 미탐색 레버는 **임베딩 모델 자체의 교차언어 성능**이다.
- **최약점과 정합**: 교차언어 갭은 벡터 arm이 만든 갭(1-2절)이므로, 벡터 arm을 고치는 정공법은 **더 강한 다국어 임베딩 모델**이다. 리랭킹(docs/12-C)이 "not-in-pool"을 못 고치는 것과 달리, 임베딩 교체는 정답을 애초에 풀에 넣는 **recall 층**을 건드린다.
- **미판정 지점**: docs/11 §5는 "임베딩 모델 교체/GPU"를 "인프라 판단 영역, 본 분석은 코드 레벨 병목만"이라며 **명시적으로 스코프 밖**에 뒀다. docs/09 P3는 리랭커(bge-reranker) 얘기지 **retrieval용 임베딩 교체는 다룬 적 없다.** 즉 "recall을 위한 임베딩 모델 교체"는 어느 문서도 판정하지 않았다.

### 5-2. 후보 방향(참고, 확정 아님)

- 현행: `multilingual-e5-small`(384dim, CPU). 교차언어 Recall@3 50%.
- 교체 후보군: `multilingual-e5-base/large`, `bge-m3`(dense, 다국어 강세), `gte-multilingual-base` 등 **더 큰 다국어 dense 모델**. 방향은 "한↔영 교차언어 검색 품질이 e5-small보다 높은가"가 유일한 선정 기준.

### 5-3. 비용·리스크(정직하게)

- **전면 재색인**: dim이 바뀌면(384→768 등) `api_chunk.embedding` 컬럼·HNSW 인덱스 재생성 + 기존 endpoint 청크 전량 재임베딩. docs/12-B·docs/09 P2가 보류된 것과 **같은 재색인 규모**.
- **지연 회귀 리스크(중요)**: docs/11 B1이 지목했듯 **로컬 CPU 임베딩 추론이 엔드포인트 검색 지연의 지배 비용**이다. 더 큰 모델은 이 추론을 더 느리게 만든다 — 교차언어 recall↑와 **검색 지연↑의 트레이드오프**. base/large는 small 대비 수 배 느릴 수 있어, 지연 예산을 반드시 함께 측정해야 한다(docs/11 S1 부분 병렬화가 이 지연을 일부 흡수할 수 있으나 미착수).
- **메모리·다운로드**: 모델 상주 메모리·다운로드 용량 증가(현 e5-small ~471MB 대비).

### 5-4. 착수 판단 규율 — 실험 게이트 필수

docs/09 P2·P4·docs/12-B가 세운 규율을 그대로 적용한다: **재색인 규모의 작업은 P1 평가셋(84질의, 교차언어 카테고리)으로 효과를 먼저 실측한 뒤에만 착수.**

- **실험 설계**: 후보 모델 1~2개로 교차언어 카테고리 Recall@{3,5}·MRR을 e5-small 대비 측정(프로덕션 무변경, docs/09 P4·docs/13이 쓴 in-memory/픽스처 방식 재사용).
- **주의(docs/13 교훈)**: docs/13(문맥 청킹)은 **픽스처 아티팩트로 효과가 가짜였다.** 임베딩 교체 실험도 같은 함정을 경계해야 한다 — 20엔드포인트 픽스처가 교차언어 개선을 관측하기에 충분한 표본인지 먼저 확인하고, 아니면 교차언어 라벨 질의를 보강한 뒤 측정. **모델을 바꾸면 recall이 오를 것 같다는 직관만으로 재색인에 착수하지 않는다.**
- **게이트 통과 조건**: 교차언어 Recall@3가 유의미하게(예: 50%→70%+) 오르고, 그 대가인 검색 지연 증가가 후보 피더로서 수용 가능한 범위일 때만 착수 권장. 개선 미미하거나 지연이 과하면 **e5-small 유지**(YAGNI).

## 6. 사용자에게 제시할 요약

- **키워드 arm 제거·전량 벡터화**: ❌ 비권장. RRF가 단일 arm보다 전 지표 우세(실측)고, 최약점(교차언어)은 벡터 자신의 약점이라 벡터 100%로 안 풀린다. 튜닝된 FTS 자산만 버리는 순손실.
- **Qdrant 전환**: ❌ 비권장(docs/06 두 차례 판정 재확인). 스케일 동인 부재 + 관계형 메타 잔존에 따른 payload 복제·이중쓰기 + 전면 재색인. (단 대사용자 근거는 "단일 SQL 하이브리드 상실"이 아니라 이 셋으로 설명해야 한다 — 키워드 arm 제거 전제가 하이브리드 자체를 없애므로.)
- **교차언어를 정말 겨눌 거면**: 대공사(Qdrant/전량벡터)가 아니라 ① 현존 저비용 레버 `query_variants`(docs/12-A, 이미 가동), ② 신규 후보로 **임베딩 모델 교체**(5절) — 단 재색인·지연 트레이드오프 때문에 **P1 평가셋 실측 게이트를 통과할 때만** 착수. docs/13 픽스처 아티팩트 전철을 밟지 않도록 표본 유효성 먼저 확인.

> 핵심: 사용자의 방향(벡터 강화)은 겨냥 지점(교차언어 recall)은 옳으나 **수단이 과하고 역효과**다. 같은 지점을 치는 옳은 수단은 스토어 교체가 아니라 **임베딩 모델 교체(실험 게이트)** 이며, 그마저도 착수 전 실측이 선행돼야 한다.
