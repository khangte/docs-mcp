## 2. 프로젝트 개요

본 프로젝트의 목표는 Swagger/OpenAPI 문서를 수집하고 검색 가능한 형태로 정리한 뒤, 이를 **Claude에서 바로 사용할 수 있는 MCP 서버**로 제공하는 것이다.  
핵심 사용자는 개발 중 필요한 API 정보를 빠르게 찾으려는 개발자이며, 문서 검색 시스템과 MCP 서버를 분리된 단계가 아니라 하나의 통합된 결과물로 설계한다.

즉, 프로젝트의 본체는 **OpenAPI 문서 검색 기능을 내장한 MCP 서버**이며, 내부적으로는 검색 품질을 높이기 위한 수집·정규화·색인 계층을 함께 가진다.

이때 중요한 전제는, 본 프로젝트의 MCP 서버가 실제 운영 API 요청을 대신 전달하거나 응답을 중계하는 구조가 아니라는 점이다.  
OpenAPI 문서는 수집 시점에 원문과 정규화 데이터로 저장되고, 이후 검색 요청은 저장된 문서 인덱스를 기준으로 처리된다.

또한 본 프로젝트는 **MCP 서버를 통해 OpenAPI 문서를 탐색하는 연결 구조**를 전제로 한다.  
탐색 대상이 되는 OpenAPI 명세는 사전에 MCP 서버와 연결되어 있어야 하며, 서버는 해당 명세 문서에 접근하고 이를 조회할 수 있어야 한다. 클라이언트는 Swagger 문서 원본에 직접 접근하지 않고, MCP 서버가 제공하는 조회 및 탐색 기능을 통해 API 정보에 접근한다.

즉, OpenAPI 연동의 핵심은 단순히 Swagger URL을 입력하는 것이 아니라, MCP 서버가 해당 OpenAPI 문서를 읽고 필요한 엔드포인트, 파라미터, 요청/응답 스키마 등의 정보를 탐색 가능한 형태로 제공하도록 구성하는 것이다.

## 3. 추진 배경

실무에서는 Swagger UI 또는 OpenAPI 문서가 존재하더라도, 원하는 정보를 빠르게 찾기 어려운 경우가 많다.

주요 문제는 다음과 같다.

- 엔드포인트는 보이지만 어떤 API를 어떤 순서로 호출해야 하는지 한 번에 파악하기 어려움
- 요청 바디, 응답 구조, 인증 조건, 관련 스키마를 문서 곳곳에서 직접 찾아야 함
- 신규 사용자나 협업자가 전체 API 흐름을 이해하는 데 시간이 오래 걸림
- 문서가 있어도 실제 질의응답 수준의 탐색 경험은 제공하지 못함

따라서 단순 문서 조회를 넘어, **검색 가능한 구조화 문서 시스템**이 필요하다.

## 4. 문제 정의

현재 OpenAPI 문서는 주로 정적 문서 형태로 소비된다.  
이 방식에서는 사용자가 직접 문서를 열고, 태그를 이동하고, 엔드포인트를 찾고, 요청/응답 구조를 하나씩 확인해야 한다.

이 프로젝트가 해결하려는 핵심 문제는 다음과 같다.

- 필요한 API를 빠르게 찾기 어렵다.
- 요청 바디, 응답 스키마, 인증 정보를 한 번에 파악하기 어렵다.
- 관련 엔드포인트나 호출 흐름을 연결해서 이해하기 어렵다.
- 문서가 있어도 검색과 질의응답 중심의 탐색은 지원되지 않는다.

## 6. 핵심 아이디어

프로젝트의 핵심은 OpenAPI 문서를 그대로 보여주는 것이 아니라,  
**검색과 질의응답에 적합한 구조로 재정리하여 저장하는 것**이다.

문서 원문은 그대로 보관하되, 실제 검색에는 다음 단위를 사용한다.

- 엔드포인트 단위
- 요청 바디 단위
- 응답 단위
- 스키마 단위
- 설명/예시 단위

이렇게 분리하면 사용자는 다음과 같은 방식으로 더 빠르게 필요한 정보를 찾을 수 있다.

- "로그인 API"
- "403 에러"
- "토큰 재발급"
- "curl 예시"
- "인증 필요한 API"

- 즉시성 있는 실 API 호출 결과 조회보다, 문서 검색과 탐색 경험 제공에 우선순위를 둠

## 8. 문서 동기화 전략

본 프로젝트는 저장형 검색 구조를 채택하므로, 문서 최신성을 유지하기 위한 동기화 시점과 정책이 필요하다.

문서 동기화 기본 원칙은 다음과 같다.

- 검색과 상세 조회는 원칙적으로 저장된 문서 원문, 정규화 데이터, 검색 인덱스를 기준으로 수행
- 문서 최신성은 별도의 수집 및 재색인 정책으로 관리
- MCP 서버는 동기화 자체를 담당하기보다, 동기화된 검색 결과를 외부 클라이언트에 제공하는 역할에 집중

문서 수집 및 갱신 시점은 다음과 같이 정의한다.

- 최초 등록 시: OpenAPI 문서를 수집하고 원문 저장, 파싱, 색인을 즉시 수행
- 수동 갱신 시: 관리자가 특정 문서에 대해 재수집 및 재색인을 요청할 수 있음
- 주기 갱신 시: 설정된 주기에 따라 문서 변경 여부를 확인하고 필요 시 재색인 수행
- 구조 변경 감지 시: 수집한 OpenAPI 원문 전체에 대한 콘텐츠 해시를 계산하고, 이전 해시와 다를 때만 재처리

변경 감지 기준은 **콘텐츠 해시**를 기본값으로 사용한다.

- `ETag`, `Last-Modified`는 서버마다 신뢰도가 다를 수 있으므로 보조 메타데이터로만 활용
- 최종 변경 여부 판단은 저장된 원문과 신규 원문의 해시 비교로 통일
- 이 방식은 문서 제공 서버의 구현 방식과 무관하게 일관된 판단 기준을 제공

동기화 메타데이터는 다음 정보를 포함하는 방향으로 설계한다.

- 문서 원본 URL
- 최초 수집 시각
- 마지막 수집 시각
- 마지막 색인 시각
- 마지막 콘텐츠 해시
- 참고용 응답 헤더 값(`ETag`, `Last-Modified`)
- 동기화 상태(`ready`, `syncing`, `failed` 등)
- 문서 버전 또는 리비전 식별값

이 정책을 통해 검색 응답은 빠르게 유지하면서도, 문서 변경 시 재수집 근거와 시점을 명확히 관리할 수 있다.

## 9. 사용자 시나리오

### 시나리오 1. 문서 등록

관리자가 OpenAPI URL을 입력하면 시스템이 `/openapi.json`을 수집하고, 문서를 파싱하여 저장한다.

등록이 완료되면 해당 OpenAPI 문서는 MCP 서버의 탐색 대상 문서로 연결되며, 이후 클라이언트는 MCP 도구를 통해 이 문서를 조회할 수 있다.

### 시나리오 2. 문서 검색

사용자가 "로그인 API" 같은 검색어를 입력하면 시스템은 관련 엔드포인트를 점수화해 반환한다.

### 시나리오 3. 상세 조회

사용자가 특정 엔드포인트를 선택하면 다음 정보를 보여준다.

- 메서드
- 경로
- 설명
- 요청 바디
- 응답 구조
- 관련 스키마
- 예시 데이터

### 시나리오 4. 예시 생성

사용자가 특정 API의 요청 예시를 원하면 시스템이 문서 구조를 바탕으로 예시 코드를 생성한다.

예시 출력 형식은 다음 중 하나를 선택할 수 있다.
- curl
- fetch
- axios
- python requests

### 시나리오 5. MCP 사용

사용자는 Claude에서 MCP 도구를 통해 OpenAPI 문서를 검색하고 필요한 결과를 바로 가져올 수 있다.

이때 Claude의 질의는 MCP 서버를 통해 내부 검색 시스템으로 전달되며, 응답은 저장된 OpenAPI 문서 인덱스에서 조회된 결과를 기반으로 생성된다.
사용자는 문서 원본 URL에 직접 접근하지 않고도, MCP 서버가 제공하는 검색·상세조회·예시생성 도구만으로 필요한 API 정보를 확인할 수 있다.

## 10. 전체 아키텍처

### 10-1. 클라이언트 요청 시작 흐름

**클라이언트 요청 → Claude → MCP 서버 → 검색 서비스 → PostgreSQL + pgvector → MCP 서버 → Claude → 클라이언트**

실제 사용 시 탐색 흐름의 시작점은 클라이언트의 요청이다.

1. 사용자가 Claude에서 API 문서를 검색하거나 상세 정보를 요청한다.
2. Claude는 연결된 MCP 서버 도구를 호출한다.
3. MCP 서버는 검색 서비스에 질의를 전달한다.
4. 검색 서비스는 저장된 정규화 데이터와 벡터 인덱스를 조회한다.
5. 결과는 MCP 서버를 통해 Claude에 반환되고, 최종적으로 클라이언트가 확인한다.

이 흐름은 사용자가 Swagger 원문에 직접 접근하지 않고, MCP 서버를 통해 탐색 경험을 얻는다는 점을 보여준다.

### 10-2. 통합 아키텍처

**OpenAPI 소스 → 수집기 → 정규화 파서 → PostgreSQL + pgvector → 검색 서비스 → MCP 서버 → Claude/사용자**

구성 요소는 다음과 같다.

- `ingestor`: OpenAPI 문서 수집
- `parser`: 엔드포인트/스키마 정규화
- `indexer`: 검색용 chunk 및 embedding 생성
- `search service`: 키워드/벡터 검색
- `mcp server`: 검색/상세조회/예시 응답을 Claude에 도구 형태로 노출

여기서 MCP 서버는 운영 API 프록시가 아니라 검색 서비스 어댑터에 가깝다.

- 문서 수집과 색인은 사전 처리 단계에서 수행
- 사용자 질의 시에는 저장된 정규화 데이터와 검색 인덱스를 조회
- 필요 시 문서 재수집 또는 재색인을 별도 작업으로 실행
- MCP 서버는 사전에 연결된 OpenAPI 명세 집합을 기준으로 탐색 가능한 도구를 노출

### 10-3. MCP 서버와 OpenAPI 문서 연결 방식

MCP 서버와 OpenAPI 문서의 연결은 다음 흐름으로 이루어진다.

1. 관리자가 OpenAPI 문서 URL 또는 명세 원본을 등록한다.
2. 수집기가 해당 명세를 읽어 원문을 저장하고 정규화 및 색인을 수행한다.
3. MCP 서버는 색인된 문서를 탐색 가능한 도구 집합으로 노출한다.
4. 클라이언트는 원본 문서가 아니라 MCP 서버 도구를 통해 엔드포인트, 파라미터, 요청/응답 스키마를 조회한다.

이 구조에서 중요한 점은 다음과 같다.

- OpenAPI 명세는 MCP 서버가 접근 가능한 범위 안에 있어야 함
- 문서 원본과 탐색 인터페이스는 분리되며, 사용자 접근 지점은 MCP 서버로 통일됨
- MCP 서버는 연결된 문서를 그대로 전달하는 것이 아니라 탐색 가능한 검색 결과로 재구성해 제공함

### 10-4. 접근 방식 상세 설명

본 프로젝트의 접근 방식은 단순 문서 프록시가 아니라, **OpenAPI 문서를 탐색 가능한 검색 자산으로 변환한 뒤 MCP 도구로 노출하는 방식**이다.

전체 처리 흐름은 다음과 같다.

1. 관리자가 OpenAPI 문서 URL을 등록한다.
2. `src/services/ingestor/openapi_fetcher.py`가 원문 명세를 수집한다.
3. `src/services/parser/openapi_parser.py`가 엔드포인트, 파라미터, 요청/응답 스키마를 분리한다.
4. `src/services/indexer/chunk_builder.py`가 검색 단위를 구성하고, `embedding_provider.py`가 벡터를 생성한다.
5. 정규화된 데이터와 검색용 청크를 PostgreSQL + pgvector에 저장한다.
6. `src/services/search/search_service.py`가 키워드 검색과 벡터 검색 결과를 통합한다.
7. `src/mcp_server.py`가 검색 결과를 Claude가 사용할 수 있는 MCP 응답 형태로 변환한다.

이 접근 방식을 선택한 이유는 다음과 같다.

- 문서를 한 번 구조화해두면 이후 질의 응답 속도를 안정적으로 유지할 수 있음
- 키워드 검색과 의미 기반 검색을 함께 적용할 수 있음
- 엔드포인트, 스키마, 예시 응답을 분리해서 더 정밀한 탐색 경험을 제공할 수 있음
- Swagger 원문 구조에 직접 의존하지 않고, MCP 서버 관점의 일관된 응답 포맷을 만들 수 있음

### 10-5. 질의 처리 책임 분리

본 프로젝트에서 중요한 설계 원칙은 **사용자 질의 해석 책임**과 **문서 검색 실행 책임**을 분리하는 것이다.

각 계층의 역할은 다음과 같이 정의한다.

- `Claude`: 사용자의 자연어 요청을 이해하고, 어떤 MCP 도구를 호출할지 결정하며, 필요한 인자를 구조화한다.
- `MCP 서버`: Claude가 호출한 도구 요청을 받아 내부 검색 서비스에 전달하고, 결과를 MCP 응답 형식으로 반환한다.
- `검색 서비스`: 저장된 정규화 데이터와 검색 인덱스를 기준으로 실제 검색, 상세 조회, 예시 생성 로직을 수행한다.
- `수집/파싱/색인 계층`: OpenAPI 문서 수집, 정규화, 청크 생성, 임베딩 생성 같은 사전 처리 작업을 담당한다.

이때 중요한 점은 다음과 같다.

- 사용자 질의 자체를 Claude가 모두 검색용 데이터로 정규화해 검색을 대신 수행하는 구조는 채택하지 않음
- Claude는 검색 엔진이 아니라, 도구 선택과 인자 구성 역할을 담당함
- 문서 정규화와 검색 인덱스 생성은 질의 시점이 아니라 서버 내부 사전 처리 단계에서 수행함
- 실제 검색 정확도와 결과 일관성은 MCP 서버 내부 검색 서비스가 책임짐

예를 들어 사용자가 "POST 로그인 API 중 401 응답 설명 있는 것 찾아줘"라고 요청하면 처리 흐름은 다음과 같다.

1. Claude가 요청 의도를 해석한다.
2. Claude가 `search_endpoints` 도구를 선택하고, 필요하면 `method=POST`, `status_code=401` 같은 인자를 구성한다.
3. MCP 서버가 이 요청을 검색 서비스에 전달한다.
4. 검색 서비스가 저장된 인덱스를 조회해 결과를 반환한다.

즉, **질의 해석은 Claude가 담당하고, 검색 실행은 MCP 서버가 담당하는 구조**가 본 프로젝트의 기준 방향이다.

## 13. 데이터 설계 방향

핵심 테이블은 다음과 같이 구성한다.

- `api_document`: 문서 원문과 메타데이터
- `api_endpoint`: 엔드포인트 기본 정보
- `api_parameter`: 파라미터 정보
- `api_request_body`: 요청 바디 정보
- `api_response`: 응답 정보
- `api_schema`: 컴포넌트 스키마 정보
- `api_chunk`: 검색용 분할 텍스트와 임베딩
- `document_sync_history`: 문서 수집/재수집 이력
- `qa_history`: 질의 이력

설계의 핵심은 **원문 저장**과 **검색 구조 저장**을 분리하는 것이다.

- 원문은 추적, 재색인, 검증용으로 사용
- 정규화 데이터와 chunk는 검색 및 응답 생성용으로 사용
- 동기화 이력은 최신성 판단과 장애 분석용으로 사용

## 15. 구조 비교 및 트레이드오프

본 프로젝트에서 고려한 두 가지 구조는 다음과 같다.

### 15-1. 저장형 검색 구조

OpenAPI 문서를 미리 수집하고 저장한 뒤, 정규화와 색인을 거쳐 검색에 사용하는 방식이다.

장점은 다음과 같다.

- 검색 응답 속도가 빠름
- 키워드 검색과 벡터 검색 품질을 높이기 쉬움
- 엔드포인트, 요청 바디, 응답, 스키마를 관계형으로 재구성 가능
- 문서 버전 추적과 재색인 관리가 쉬움
- 외부 문서 서버 장애 시에도 저장된 데이터를 바탕으로 조회 가능

단점은 다음과 같다.

- 문서 최신성을 유지하기 위한 동기화 정책이 필요함
- 수집, 파싱, 색인 파이프라인 구현 비용이 있음
- 저장 공간과 색인 관리 비용이 추가됨

### 15-2. 실시간 요청 구조

사용자 요청이 들어올 때마다 외부 OpenAPI 문서를 직접 조회하거나, 필요 시 운영 API에 가까운 방식으로 실시간 요청을 보내는 구조다.

장점은 다음과 같다.

- 항상 최신 문서를 바로 조회할 가능성이 높음
- 초기 구현은 단순할 수 있음
- 별도 저장소와 색인 파이프라인 없이 시작 가능함

단점은 다음과 같다.

- 매 요청마다 외부 의존성이 생겨 응답 속도와 안정성이 떨어질 수 있음
- 검색 품질을 높이기 위해 매번 파싱과 정규화가 필요해 비효율적임
- 문서 버전 추적과 변경 이력 관리가 어려움
- 다수 문서를 통합 검색하거나 추천 기능을 붙이기 어려움

### 15-3. 본 프로젝트의 선택

본 프로젝트는 문서 검색 품질, 응답 속도, 구조화된 탐색 경험을 우선하기 때문에 저장형 검색 구조를 기본 전략으로 채택한다.

다만 최신성 문제를 보완하기 위해, 문서 등록 시 수집, 수동 재수집, 주기 갱신, 변경 감지 기반 재색인 정책을 함께 운영하는 방향으로 설계한다.

핵심 트레이드오프는 다음과 같다.

- **저장형 검색 구조 채택**: 구현과 운영 복잡도는 높아지지만 검색 품질과 응답 속도를 확보할 수 있음
- **실시간 프록시 구조 배제**: 최신성은 조금 양보하지만, 외부 문서 서버 상태에 덜 흔들리는 안정적인 탐색 경험을 제공할 수 있음
- **MCP 서버 중심 인터페이스**: Swagger 원문 직접 접근보다 한 단계 추상화가 생기지만, Claude와 다른 MCP 클라이언트에서 동일한 방식으로 사용할 수 있음
- **예시 코드 생성 제공**: 구현 범위는 늘어나지만 실제 개발 중 바로 활용할 수 있는 생산성 이점을 얻을 수 있음

## 16. 개발 추진 방향

본 프로젝트는 개발 단계를 순차적으로 분리하기보다, 전체 기획 범위를 기준으로 바로 통합 구현하는 방향으로 진행한다.

핵심 구현 범위는 다음과 같다.

- OpenAPI 문서 수집 및 원문 저장
- 문서 정규화와 검색 인덱스 구성
- 키워드 및 벡터 기반 검색
- 엔드포인트 상세 조회
- 요청 예시 생성
- 문서 동기화 관리
- Claude에서 사용할 MCP 도구 제공

즉, 검색 시스템과 MCP 서버를 따로 나누어 개발하기보다, 처음부터 MCP 사용 시나리오를 기준으로 전체를 한 번에 구성한다.
