# 구현 여정 — 로드맵 0~5는 실제로 어떻게 만들어졌나

이 문서는 docs-mcp 의 **RAG 로드맵 6개 항목이 실제 저장소에서 어떤 순서로, 어떤 판단을
거쳐 구현됐는지**를 커밋·설계문서 단위로 추적한 기록이다. 결과만 요약하지 않고 **순서가
왜 그랬는지, 중간에 뒤집힌 결정이 무엇인지, 재작업·재측정이 왜 필요했는지**를 남긴다.

- 대상 기간: **2026-07-27 ~ 2026-08-14** — 실제 구현이 이뤄진 구간이다. 그 이전에는
  틀만 잡아둔 상태로 실작업이 없었다(§0).
- 근거: 해당 구간 커밋, Alembic 마이그레이션 **12개**, `docs/exec_plans/`,
  `docs/adr/` 4건, `docs/architect-review/` 34건
- 현재 상태 문서: 구조는 [`ARCHITECTURE.md`](../ARCHITECTURE.md), 검색 로직은
  [`search-flow.md`](search-flow.md), 운영은 [`operations.md`](operations.md)
- 초기 기획서는 [`archive/plan.md`](archive/plan.md) 에 아카이브돼 있다(현행 아님)

## 0. 시작점 — 틀만 있던 상태에서 출발했다

착수 이전에도 저장소에는 골격이 있었다. 진입점과 서비스 계층 디렉터리, 그리고 방향을
적어둔 [ADR-0001](adr/0001-storage-search-structure.md)(실시간 프록시가 아닌 저장형 검색),
[ADR-0002](adr/0002-pgvector-hybrid-search.md)(pgvector 하이브리드 검색),
[ADR-0003](adr/0003-read-only-mcp-boundary.md)(읽기 전용 경계) 정도다.

다만 **그건 결정만 적힌 틀이었고 실작업은 없는 상태였다.** 저장은 SQLite, 벡터 검색은
프로세스 메모리에 올린 인덱스, 임베딩은 의미 유사도가 없는 결정적 해시 placeholder,
마이그레이션 도구는 없음. ADR-0002 가 선언한 pgvector 하이브리드도 문서상 결정일 뿐
구현이 붙어 있지 않았다.

**이 문서가 다루는 것은 그 틀에 실제 구현을 채워 넣은 2026-07-27 이후 구간이다.**
아래 로드맵 매핑도 전부 그 안에서 일어난 일이다.

| 로드맵 항목 | 실제 구현 시점 | 핵심 커밋 |
| --- | --- | --- |
| 0. 환경 세팅 (postgres+pgvector, alembic) | 2026-07-27 | `1adda21` |
| 1. 메타데이터 스키마 | 2026-07-27 착수 → `project` 는 2026-08-03 | `dfbe6143212a` → `34c6fac` |
| 2. 청킹 전략 | Markdown/CSV 2026-07-27 → sub-chunking 2026-08-13 | `b504bf7` → `546f8e4` |
| 3. Indexing Pipeline (모델 하나 고정) | 2026-08-08 (**3번째 시도**) | `be774dd` |
| 4. 검색 품질 실험·튜닝 | 2026-08-08 ~ 08-13 | `c197ec9` ~ `5015303` |
| 5. 배치 자동화 | 2026-08-13 | `afceaf7` ~ `7689cb5` |

로드맵 순서와 실제 순서가 어긋난 지점은 두 곳이고, 둘 다 이 구간 안에서 생겼다:

1. **항목 3의 "임베딩 모델 하나 고정" 이 한 번에 되지 않았다.** 해시 placeholder →
   관리형 API → 로컬 모델로 두 번 갈아 끼운 뒤에야 고정됐다(§4).
2. **항목 3에 묶여 있던 FTS 적재가 뒤로 밀렸다.** 벡터 arm 이 먼저 서고, 키워드 arm 을
   Postgres FTS 로 이관하고 RRF 로 융합한 것은 2026-08-08 이다(§4 후반).

반대로 **로드맵이 옳았던 부분은 항목 4·5의 위치다.** "평가셋 만들고 측정한 다음 튜닝",
"수동 검증 끝난 뒤 자동화" 는 실제로 그 순서로 지켜졌고, 지켜진 덕에 여러 개선안이
**측정 결과로 기각**될 수 있었다(§5).

- 개명(12번)의 여파는 문서에까지 남았다 — `search-flow.md` 가 `api_chunk`/`ApiDocument`

## 3. 항목 2 — 청킹 전략: "1~2종 먼저" 를 지켰고, 그 대가는 8월에 청구됐다

### 확장 순서

1. **OpenAPI endpoint/schema 청크** — 초기 틀에 이미 있던 형태. 엔드포인트 1개 = 청크 1개.
2. **Markdown/CSV 섹션** (2026-07-27 `b504bf7`) — 로드맵이 말한 "헤딩 단위". `api_section`
   테이블 + `doc_type` 자동 판별(`document_router.py`).
3. **PDF/DOCX** (2026-08-03 `c2dda0a`, 설계 `exec_plans/PDF_DOCX_PLAN.md`) — 텍스트 추출 후
   markdown 과 같은 섹션화 경로에 합류.
4. **Drive 경유 XLSX/PPTX** (2026-08-05 `5625039`).

### 8월에 드러난 맹점 — 512토큰 조용한 절단

`b97b5d1`(2026-08-12) 이 문제를 문서화했다:
[doc/16 "긴 섹션의 무상한 단일 청크화 + 512토큰 조용한 truncation"](architect-review/16-long-section-chunking-blindspot.md).
섹션을 헤딩 단위로만 자르면 긴 섹션이 청크 1개가 되고, e5-small 의 512토큰 상한을 넘는
뒷부분은 **경고도 없이 임베딩에서 사라진다.** 검색이 안 되는데 이유가 보이지 않는 결함이었다.

대응은 한 번에 하지 않고 게이트를 걸어 단계적으로 갔다 — 이 절이 이 문서에서 가장
"과정다운" 부분이다:

| 단계 | 산출물 | 성격 |
| --- | --- | --- |
| 진단 먼저 | `855a5be` 긴 섹션 진단 스크립트 + truncation 경고 로깅 | **고치기 전에 관측 가능하게** 만들었다 |
| 대안 비교 | doc/24 parent-child 청킹 vs 현행 | 그린필드 설계와 실제 코드 비교 |
| 무조건 전환 기각 | [doc/25](architect-review/25-unconditional-n1-vs-gated-subchunking.md) | "지금 무조건 N:1로 바꾸자" 를 **게이트형 조건부**로 반려 |
| 리뷰 판정 | [doc/27](architect-review/24-parent-child-chunking-greenfield-vs-actual.md) | reviewer 지적 판정, 섹션/스키마 헤지 유지 결정(`38ded98`) |
| 구현 | `0383667` splitter → `546f8e4` 실배선 | Phase2, 설계 doc/23 |
| 파생 결함 수정 | `fe53e73` schema 청크 `ref_id` 를 바운드 `schema_id` 로 교체 | 절단이 **크래시**로 드러난 근본 수정, doc/29 |

핵심은 "긴 섹션을 쪼갠다"는 뻔한 결론에 도달하기까지 **doc/16 → 24 → 25 → 27 네 개의
판정 문서를 거쳤다**는 점이고, 그 사이에 무조건 전환안이 한 번 반려됐다는 점이다.

## 4. 항목 3 — Indexing Pipeline: 임베딩 모델을 "하나 고정"하는 데 세 번 걸렸다

로드맵의 "임베딩 모델 하나 고정(로컬 e5-small 등 경량)" 은 결과적으로 맞았지만, 그
지점까지 **두 번의 교체**가 있었다.

| 세대 | 무엇 | 커밋 | 왜 버렸나 |
| --- | --- | --- | --- |
| 1세대 | `HashEmbeddingProvider` (결정적 해시) | 초기 틀 | 의미 유사도가 **없다**. 파이프라인 배선용 placeholder |
| 2세대 | `GeminiEmbeddingProvider` (관리형 API, 256차원) | `3fc4a17` 07-27 | 키 미설정 시 해시로 **조용히 폴백**해 벡터 검색 품질이 사라지는 운영 리스크 + 외부 비용·지연·가용성 의존 |
| 3세대 | `LocalEmbeddingProvider` (`intfloat/multilingual-e5-small`, 384차원, CPU) | `be774dd` 08-08 | **현행** |

3세대 전환 근거는 [ADR-0004](adr/0004-local-embedding-provider.md) 와 설계문서
[doc/05](architect-review/05-embedding-provider-local-model-design.md) 에 있다. 이 교체가
싼 작업이 아니었다는 점이 중요하다:

- E5 계열은 문서엔 `"passage: "`, 질의엔 `"query: "` 접두사가 필요해 **대칭
  `embed(texts)` 를 비대칭 `embed_documents`/`embed_query` 로 쪼개야 했다**(Protocol 변경).
- pgvector 컬럼은 생성 시 차원이 고정되므로 **컬럼 재생성 마이그레이션**이 필요했다
  (`ff8aa8f36266`). 기존 256차원 벡터는 새 모델과 호환되지 않아 폐기하고, 스키마
  변경과 **분리한** 전용 배치(`app/scripts/reembed.py`)로 저장된 청크 텍스트만 재임베딩했다.
- "벡터 폴백을 켤지" 판단 기준이 "Gemini 키 유무" 에서 "백엔드가 `local` 인지"로 바뀌었다.
- 부수적으로 모델 다운로드 용량 추정이 틀렸음이 실측으로 드러나 정정됐다
  (`cbc6312` ~120MB → **~471MB**). 배포 환경에서 모델을 미리 캐시(`HF_HOME`)해두라는
  권고가 여기서 나왔다.

### 벡터 하나로는 부족했다 — 키워드 arm 과 RRF

로드맵은 "벡터+FTS 컬럼 적재" 를 한 항목으로 묶었지만 실제로는 FTS 가 나중이다.
키워드 검색은 오랫동안 **애플리케이션 레벨 토큰 매칭**이었고(ADR-0002 말미가 "Keyword
Search는 아직 tsvector가 아님(TODO)" 이라고 적어둔 그대로), 2026-08-08 에 한꺼번에 정리됐다:

1. `aa4de84` 키워드 검색을 Postgres FTS(tsvector+GIN)로 이관 — 설계
   [doc/04](architect-review/04-search-p1-keyword-fts-design.md). 한글·경로 세그먼트·혼합
   복합어를 잡기 위해 ASCII↔한글 경계에 공백을 삽입하는 `TEXT_TSV_EXPRESSION` 을 도입했다.
2. `33d1dbe` **RRF 순위 융합** 도입 — 재검토
   [doc/07](architect-review/07-search-rrf-reevaluation.md). 이전 동작(키워드 우선, 0건일
   때만 벡터)은 `fallback` 전략으로 **롤백 스위치로 보존**했다. 이 보존이 §5 에서 두
   전략을 나란히 측정할 수 있게 만든다.
3. `c197ec9` 평가셋 20건 추가 — 즉 **RRF 를 넣은 그날 측정 수단도 같이 만들었다.**

### 벡터 스토어를 바꾸자는 안은 기각됐다

[doc/06 pgvector 유지 vs Qdrant 전환](architect-review/06-vector-store-qdrant-vs-pgvector.md)
에서 검토 후 **pgvector 유지 확정**. 이후 doc/14 에서 "키워드 arm 제거·전량 벡터화 +
Qdrant" 로 한 번 더 재검토됐고 다시 기각됐다(`9118686`). 같은 방향이 두 번 제기되고
두 번 기각된 기록이 남아 있다.

## 5. 항목 4 — 검색 품질 실험·튜닝: 이 프로젝트에서 가장 긴 구간이자, 대부분이 "안 함" 결론

로드맵의 "평가 질의셋 20개 정도로 recall/MRR 측정 후 반복" 이 실제로 어떻게 굴러갔는지가
이 절이다. **결과적으로 이 구간은 개선을 많이 만든 구간이 아니라, 개선안을 많이 기각한
구간이다** — 그리고 그게 평가셋을 먼저 만든 목적이었다.

### 5.1. 평가셋: 20 → 84 → 실 코퍼스

| 단계 | 규모 | 커밋 | 성격 |
| --- | --- | --- | --- |
| 1차 | 20질의 | `c197ec9` 08-08 | RRF vs fallback 비교용 자체 스펙 |
| 지표 모듈 | MRR/nDCG@10/Recall@{1,3,5,10} | `731d43c` 08-10 | 손계산 제거 |
| 2차 | **84질의**(실패 taxonomy 8종 × 8질의 이상) | `97f3c2d` 08-10 | 계획 `exec_plans/eval-set-expansion-plan.md`. 현재 픽스처는 100질의 |
| 3차 | 실 코퍼스 20질의 (Stripe/GitHub 실제 OpenAPI) | `143478c` 08-13 | 설계 [doc/28](architect-review/27-search-quality-eval-real-corpus-design.md) |

**20질의와 84질의가 다른 답을 줬다**는 것이 확장의 정당화다. 20질의에서 RRF 는 top-1
80% 불변이었지만, 84질의 확장셋에서는 Recall@1 이 60%→69% 로 **개선**됐다
([doc/09](architect-review/09-search-quality-post-rrf.md) §):

| 지표 | fallback | rrf | 차이 |
| --- | --- | --- | --- |
| Recall@3 | 79% | 88% | +9pt |
| Recall@5 | 82% | 88% | +6pt |
| Recall@10 | 89% | 95% | +6pt |
| MRR | 0.704 | 0.788 | +0.084 |

### 5.2. 자체 스펙에서 실 코퍼스로 옮기니 점수가 무너졌다

실 코퍼스(Stripe/GitHub) 20질의에서의 수치는 위와 자릿수가 다르다 —
[doc/30](architect-review/29-search-quality-eval-real-corpus-results.md) §13.1 마감 재측정
기준 최고 조건(변형 포함 rrf)이 **Recall@10 50%, MRR 0.248, nDCG 0.308** 이다.
자체 제작 평가셋의 88~95% 와 실제 대형 스펙에서의 50% 사이 간격이 이 프로젝트가 확보한
가장 값나가는 관측이고, 그래서 README 는 이 도구를 **"후보 피더"** 로, 품질 지표를
recall@k 로 규정한다.

### 5.4. 실제로 채택된 개선 3건과 그 뒤의 재측정

실 코퍼스 측정이 드러낸 실패 카테고리에 대응해 세 건만 반영했다:

1. `e0794bf` **교차언어(C2) recall 개선** — `query_variants` 를 벡터 arm 에도 라우팅
   (원본+변형 각각 임베딩 → 후보별 등수 최솟값 병합). doc/30 §7.2.
   이 변경은 doc/12 가 **"벡터 arm 은 손대지 않는다"** 고 명시했던 결정을 뒤집은 것이고,
   뒤집은 이유는 교차언어에서는 벡터 arm 이 유일한 신호인데 원본 한글 질의만으로는
   약하다는 측정 결과였다.
2. `0f94280` 엔드포인트 청크에 **request body 필드명 색인 추가** (C7 색인 누락)
3. `cb993e4` 엔드포인트 청크 **필드 순서를 구조필드 우선으로 재배치**

그리고 여기서 이 구간의 성격이 가장 잘 드러나는 일이 일어난다 — architect 가
**"§1 원표는 stale 이다, 세 변경을 모두 반영한 전체 지표 표가 어디에도 없다"** 고 판정해
(doc/30 §12.4) **전체 재측정을 요구**했다. 재측정 결과(§13)에서 순 지표는 올랐지만
**C5 카테고리에 신규 회귀**가 나타났고, 그 원인을 다시 판정한 뒤(§14) 라운드를 종결했다.
종결 조건은 "모든 카테고리를 고쳤다" 가 아니라 **"n=20 표본에서는 이 이상 판단할 수
없다, 카테고리별 n 을 키운 평가셋이 선행 게이트다"** 였다(§12.5).

## 6. 항목 5 — 배치 자동화: 대상을 한 번 잘못 잡았다

로드맵은 "최후순 — 수동 검증 끝난 뒤 자동화" 라고 했고 실제로 마지막(2026-08-13)에 했다.
다만 **무엇을 자동화할지가 처음엔 다르게 판정됐다.**

### 6.1. 1차 판정 — 대상은 평가 배치, refresh_index 는 반려

사용자 요청("배치 자동화를 적절하게 적용해야돼")에 대상이 없었다.
[doc/31](architect-review/30-eval-batch-automation.md) 은 후보를 전부 열거한 뒤
**(a) 검색품질 평가 재측정 배치**를 대상으로 특정하고, 문서 재색인 쪽에 대해서는
§2 에서 **명시적 반대 판정**을 냈다:

> MCP stdio 서버는 클라이언트가 세션마다 띄우는 단명 프로세스다. 여기에 크론·APScheduler 를
> 내장하면 세션 수만큼 스케줄러가 중복 기동하고, 클라이언트가 서버를 내리면 스케줄도 죽는다.
> **판정: 서버 프로세스 내부 스케줄링은 반려.** 그 요구가 아직 제기된 적 없으므로 지금은
> 만들지 않는다(YAGNI).

### 6.2. 2차 — lead 가 대상을 정정, 반려 근거는 유지

lead 가 "대상은 `refresh_index` 다. 내부 스케줄링 반려는 유지하되 **서버 밖 상주 러너**
방향으로 설계하라" 고 지시해 [doc/32](architect-review/31-refresh-index-batch-automation.md)
가 나왔다. 여기서 주목할 점은 **1차 판정을 뒤집지 않고 범위만 갈랐다**는 것이다 —
"서버 안에 스케줄러를 두지 않는다" 는 유지하고, "스케줄 주체를 OS 로 옮긴다" 만 추가했다.
그 결과가 지금 구조다: **앱은 스케줄을 모르고, 한 번 돌고 종료하는 배치 진입점만 갖는다.**

자동화의 명분도 "편의" 가 아니라 **검색 정확성**으로 다시 잡혔다 — `search_documents` 는
1단계에서 메타 캐시 후보가 0건이면 본문 fetch 없이 빈 리스트를 반환하므로,
**메타 캐시에 없는 문서는 검색 경로에 진입조차 못 한다.**

### 6.3. 구현과 그 과정에서 나온 결함

| 커밋 | 내용 |

## 7. 이 프로젝트에서 반복된 작업 패턴

7~8월 구간을 통째로 보면 같은 루프가 반복된다.

1. **검토 문서를 먼저 쓴다** (`docs/architect-review/NN-*.md`) — 대안을 나열하고 판정을 적는다.
   34건 중 상당수가 **"코드 미수정, 방향 검토 only"** 상태로 시작한다.
2. **측정 수단을 개선과 같은 시점에 만든다** — RRF 도입(`33d1dbe`)과 평가셋(`c197ec9`)이
   같은 날이다.
3. **고치기 전에 관측 가능하게 만든다** — 긴 섹션 문제는 진단 스크립트와 경고 로깅
   (`855a5be`)이 splitter(`0383667`)보다 하루 먼저 들어갔다.
4. **롤백 스위치를 남긴다** — RRF 도입 시 이전 동작을 `fallback` 전략으로 보존했고,
   그 덕에 두 전략을 나란히 측정할 수 있었다.
5. **실측으로 자기 안을 기각한다** — P4 K 스윕(null result), e5-base(HOLD), Qdrant(2회 기각),
   무조건 N:1 청킹(반려).
6. **결정을 뒤집을 때는 근거를 남기고 뒤집는다** — 서버 LLM 질의확장은 도입(`84df194`)
   **직후** 클라이언트 제공 방식으로 전환됐고(`fb7b98f`), 판단은 호출측 LLM 의 몫이라는
   원칙으로 굳어져 이후 `query_variants` 규약 전체의 근거가 된다.
